## 트랜잭션 기초
### 정의
- **DB의 상태를 변화시키는 하나의 논리적인 작업 단위**이다.
- 비즈니스 로직에 따라 하나 이상의 SQL 문으로 구성된다.
- 트랜잭션 내부의 모든 작업은 전부 성공하여 DB에 반영되거나(Commit), 전부 실패하여 작업 이전의 초기 상태로 되돌려져야(Rollback) 한다.

### 4가지 속성 (ACID)
#### 원자성 (Atomicity)
- 트랜잭션은 **원자적**이어야 한다.
  - 즉, **트랜잭션 내의 연산들은 모두 성공하거나, 모두 실패**해야 한다.
- **InnoDB 내 구현 원리:**
  - 시스템 오류나 롤백 요청 시, **Undo Log에 백업해 둔 변경 이전의 데이터를 참조하여 트랜잭션 시작 전 상태로 복구**한다.

#### 일관성 (Consistency)
- 트랜잭션은 **DB의 일관성을 유지**해야 한다.
  - 이는 **트랜잭션이 DB에서 정의된 규칙과 제약 조건을 준수해야 함**을 의미한다.
  - 즉, **트랜잭션 전후에도, 트랜잭션 중에도 DB의 일관성은 유지**되어야 한다.
- **무결성과 일관성의 차이:**
  - **무결성 (Integrity):** 
    - **데이터 자체가 유효하고 정확한가**를 의미한다.
    - DB에 저장된 값들이 오염되지 않은(사전에 정의된 규칙이나 제약 조건을 위반하지 않은) 상태이다.
    - 예) PK는 중복될 수 없다(개체 무결성), 나이 컬럼에 음수나 문자가 들어갈 수 없다(도메인 무결성) 등
  - **일관성/정합성 (Consistency):**
    - **데이터 간의 상태나 관계에 모순이 없는가**를 의미한다.
    - 트랜잭션 전후로 무결성 제약 조건이 지속적으로 유지되는(데이터 간의 논리적 합이나 관계에 모순이 없는) 상태이다.
    - 예) 계좌 이체 시, 트랜잭션 전후로 두 계좌 잔액의 총합은 항상 동일해야 한다.
- **DB 제약 조건(Constraint):** 데이터의 무결성을 보장하기 위해 DB에 설정하는 규칙이다.
  - **PRIMARY KEY:** 테이블 내의 각 레코드를 고유하게 식별한다. (`UNIQUE` + `NOT NULL` 속성 포함)
  - **FOREIGN KEY:** 다른 테이블의 기본 키를 참조하여 테이블 간의 참조 무결성을 유지한다.
  - **UNIQUE:** 해당 컬럼에 중복된 값을 허용하지 않는다.
  - **NOT NULL:** 해당 컬럼에 NULL 값을 허용하지 않는다.
  - **CHECK:** 지정된 조건식을 만족하는 유효한 데이터만 입력을 허용한다.

#### 격리성 (Isolation)
- **트랜잭션 간에는 격리**되어야 한다.
  - 이는 **각 트랜잭션은 서로 영향을 주지 않고, 동시에 실행되는 다른 트랜잭션에 영향을 받지 않아야 함**을 의미한다.
  - 즉, **동시에 실행되는 여러 트랜잭션이 서로의 중간 작업 결과를 참조하거나 간섭할 수 없도록 격리(별도의 공간에서 작업 수행)되어야** 한다.
- 완벽한 격리성을 보장하면 동시성이 크게 감소하므로, DB는 **성능과 일관성의 트레이드오프를 조절하기 위해 4단계의 격리 수준을 제공**한다.

#### 지속성 (Durability)
- **트랜잭션의 결과는 지속**되어야 한다.
  - 이는 **트랜잭션이 커밋(성공적으로 완료)되면, 해당 트랜잭션에 의한 변경 내용은 영구적으로 저장되어야 함**을 의미한다.
  - 즉, 전원 차단이나 시스템 장애가 발생하더라도, DB는 영구적으로 변경된 상태를 유지해야 한다.
- **InnoDB 내 구현 원리 (WAL, Write-Ahead Logging):**
  - 디스크 임의 접근(Random I/O)으로 인한 성능 저하를 방지하기 위해, 변경 사항을 DB에 즉시 기록하지 않는다.
    1. **메모리(InnoDB Buffer Pool)에 변경 사항을 우선 반영**하는데, 이 데이터를 **Dirty Page**라고 부른다.
    2. **디스크에는 순차적으로 빠르게 기록 가능한 Redo Log에만** 변경 내역을 먼저 남긴다.
  - 백그라운드 스레드가 특정 조건에 도달하면 메모리의 Dirty Page를 실제 DB에 일괄적으로 기록하는데, 이를 **Dirty Page Flush**라고 한다.
  - 시스템 장애 발생 시 재부팅 과정에서 Redo Log를 참조하여 커밋된 데이터를 안전하게 복구한다.

## 트랜잭션 격리 수준 (Isolation Level)
### 트랜잭션의 3가지 이상 현상 (Anomaly)
> **트랜잭션 간의 격리가 완벽하지 않을 때 발생하는 데이터 정합성 문제**이다.

#### Dirty Read
- 특정 트랜잭션이 **아직 커밋되지 않은 다른 트랜잭션의 데이터를 읽어버리는 현상**이다.
- 데이터를 수정한 트랜잭션이 롤백될 경우, 존재하지 않는 잘못된 데이터를 기반으로 로직을 수행하는 문제가 발생할 수 있다.

#### Non-Repeatable Read
- **하나의 트랜잭션 내에서 동일한 쿼리를 두 번 실행할 때**, 그 사이에 다른 트랜잭션이 기존 데이터의 값을 수정(`UPDATE`)하거나 삭제(`DELETE`)하여 **두 쿼리의 결과 값이 다르게 나타나는 현상**이다.

#### Phantom Read
- **하나의 트랜잭션 내에서 동일한 조건으로 여러 레코드를 두 번 조회할 때**, 그 사이에 다른 트랜잭션이 새로운 레코드를 삽입(`INSERT`)하여 **조건에 맞는 데이터의 수나 목록이 달라지는 현상**이다.

### 트랜잭션 격리 수준 4단계
> **동시성(성능)과 데이터 일관성 사이의 트레이드오프를 조절하기 위해 위 3가지 이상 현상을 어디까지 허용할 것인가를 정의한 기준**이다.

#### 1. READ UNCOMMITED
- **커밋되지 않은 데이터의 읽기를 허용하는 가장 낮은 격리 수준**이다.
- **Dirty Read, Non-Repeatable Read, Phantom Read가 모두 발생**한다.
- 데이터 정합성에 치명적이므로 실무에서 사용하지 않는다.

#### 2. READ COMMITED
- **커밋이 완료된 데이터만 읽기를 허용**한다. (**Oracle DB 기본 격리 수준**)
- **Dirty Read는 발생하지 않지만, Non-Repeatable Read와 Phantom Read는 발생**한다.
  - 트랜잭션 도중 다른 트랜잭션이 수정 내역을 커밋하는 경우, 변경된 데이터를 읽게 되기 때문이다.

#### 3. REPEATABLE READ
- **트랜잭션이 시작되기 전에 커밋된 내용에 대해서만 조회를 허용**한다. (**MySQL InnoDB 기본 격리 수준**)
- **기본적으로 Dirty Read와 Non-Repeatable Read가 발생하지 않으며, MySQL의 경우에는 Phantom Read 또한 발생하지 않는다.**
  - 전자의 경우, 트랜잭션 내에서 동일한 레코드를 여러 번 읽어도 항상 동일한 결과를 반환하기 때문이다.
- **그렇다면 왜 MySQL에서만 Phantom Read가 발생하지 않을까?**
  - 이는 **MySQL의 MVCC(다중 버전 동시성 제어) 덕분**이다.
  - **다른 DB는 레코드 자체에 락을 거는 방식(락 기반 매커니즘)이지만, MySQL은 트랜잭션 시작 시점에 찍어둔 스냅샷을 활용하는 방식**이기 때문이다.
  - 자세한 것은 아래 예시를 한 번 살펴보자.
- **예시:**
  - 트랜잭션 A가 10건을 조회하는 상황이라고 하자.
  - 전통적인 방식에서는 이 10건의 레코드에만 직접 락을 거는 방식이기 때문에, 다른 트랜잭션에 의해 추가되는 레코드가 조회될 수 있다.
  - 반면 MySQL에서는 트랜잭션 시작 시점의 스냅샷을 기준으로 데이터를 읽기 때문에, 다른 트랜잭션에 의해 레코드가 추가되더라도 항상 동일한 결과(이전 스냅샷)가 반환된다.

#### 4. SERIALIZABLE
- **가장 엄격한 격리 수준으로, 읽기 작업에도 공유 락(Shared Lock)을 거는 방식**이다.
- Dirty Read, Non-Repeatable Read, Phantom Read가 모두 발생하지 않지만(데이터 일관성은 완벽하지만), **동시성이 극도로 저하되기 때문에 거의 사용되지 않는 방식**이다.

## 락
### 필요성
- **MVCC를 통해 단순 조회를 처리하더라도, 데이터를 변경하는 경우에는 반드시 락을 걸어 다른 트랜잭션의 접근을 제어**해야 한다.

### 종류
#### 공유 락 (Shared Lock, S-Lock)
- **데이터를 읽을 때(Read) 거는 락**이다.
- **여러 트랜잭션이 동시에 하나의 데이터에 공유 락을 걸 수 있지만, 해당 데이터에 배타 락을 거는 것은 차단**된다.

#### 배타 락 (Exclusive Lock, X-Lock)
- **데이터를 변경할 때(Write - `INSERT`, `UPDATE`, `DELETE`) 거는 락**이다.
  - 참고로 **데이터를 변경할 때 내부적으로 발생하는 조회(`SELECT ... FOR UPDATE`)에도 배타 락이 사용**된다.
- 배타 락이 걸려 있는 데이터에는 다른 트랜잭션이 공유 락도, 배타 락도 걸 수 없다. (**독점**)

### 적용 방식
#### 비관적 락 (Pessimistic Lock)
- **데이터 충돌이 무조건 발생할 것이라고 가정하고, 트랜잭션 시작 시점에 실제 DB 락(S-Lock, X-Lock, DB 엔진이 제공하는 실제 락)을 걸어버리는 방식**이다.
  - 예) `SELECT ... FOR UPDATE`, `SELECT ... FOR SHARE`

#### 낙관적 락 (Optimistic Lock)
- **데이터 충돌이 발생하지 않을 것이라고 가정하여, 실제 DB 락을 사용하지 않는다.**
- 대신 애플리케이션 레벨(JPA 등)에서 **`version` 컬럼을 활용하여 업데이트 시점에 버전 일치 여부로 충돌을 감지**한다.

### MySQL InnoDB에서의 락
#### 인덱스
- **인덱스는 특정 컬럼에 지정하며, 실제 테이블과 분리된 별도의 자료구조**(테이블)이다.
- 특정 컬럼(예: `id`)에 인덱스를 지정하면, **DB 엔진은 해당 컬럼의 값들만 복사하여 오름차순으로 정렬한 B-Tree(트리 구조) 형태의 데이터를 별도로 생성**한다.
- 이 **인덱스 자료구조 안에는 '정렬된 컬럼 값'과 '실제 테이블 레코드의 물리적 주소(또는 PK)'가 함께 매핑되어 저장**된다.
  - PK 컬럼을 인덱스로 지정하면 실제 테이블 레코드의 물리적 주소가 저장되고, PK가 아닌 컬럼을 인덱스로 지정하면 PK가 매핑되어 저장된다. 

#### 특징: 인덱스 기반의 락
- InnoDB의 락은 실제 (테이블의) 데이터 레코드 대신 **인덱스 레코드를 대상**으로 한다.
- 조건절(`WHERE`)에 인덱스가 없는 경우 풀 테이블 스캔(FTS)이 발생하여 테이블의 모든 레코드에 락이 걸릴 수 있다.
  - 참고로 락은 **조건에 맞는 인덱스 레코드를 하나씩 탐색하는 과정에서 개별적으로 걸리는 것**이지, 조회 결과라는 하나의 덩어리에 걸리는 것이 아니다. 

#### 세부 락 종류
- **레코드 락 (Record Lock):**
  - 데이터 레코드(테이블의 레코드)가 아니라, 인덱스 레코드(인덱스의 레코드)에 락을 거는 방식이다.
- **갭 락 (Gap Lock):**
  - 레코드와 레코드 사이의 간격(Gap, **실제 데이터가 존재하지 않는 논리적 구간**)에 락을 걸어, 다른 트랜잭션이 해당 구간에 새로운 데이터를 삽입(`INSERT`)하는 것을 차단한다.
- **넥스트 키 락 (Next-Key Lock):**
  - 레코드 락과 갭 락의 결합 형태로, **특정 인덱스 레코드와 이전 레코드(인덱스 트리 기준) 사이의 간격 전체에 락을 거는 방식**이다.
  - 넥스트 키 락 덕분에 MySQL은 `REPEATABLE READ` 격리 수준에서 Phantom Read가 발생하지 않는다.
  - 참고로 **갭(`INSERT`을 막아야 하는 구간)의 바로 다음(Next)에 위치한 인덱스 키(Key)까지 락을 건다**는 의미에서 넥스트 키 락이라고 명명되었다.
  - 아래 예시를 보면 조금 이해가 될 것이다.

#### 넥스트 키 락 예시
> **`age` 컬럼이 인덱스로 잡혀있는 테이블에서, 가령 트랜잭션 A가 age를 18에서 16으로 바꾼다고(`UPDATE`) 해보자.**

1. **트랜잭션 A 탐색 및 락 획득:**
   - `UPDATE` 쿼리가 실행되는 순간, 엔진은 인덱스 레코드 `18`을 찾은(예: `SELECT * FROM t WHERE age=18 FOR UPDATE`) 후 `13~18` 구간에 넥스트 키 락을 건다. 
2. **트랜잭션 B 진입 및 블로킹:**
   - 이 시점에 트랜잭션 B가 `17`을 `INSERT`하려고 시도하더라도, 해당 구간에 넥스트 키 락이 걸려있기 때문에 대기(Blocking) 상태에 빠진다.
3. **트랜잭션 A 수정 완료 및 락 유지:**
   - A가 `UPDATE` 쿼리 작업을 마친 상황이어도, `COMMIT`하지 않았다면 락이 유지되기 때문에 여전히 B는 블로킹되어 있는 상태이다.
4. **트랜잭션 A 커밋 및 트랜잭션 B 실행:**
   - A가 `COMMIT`을 호출하여 락이 일괄 해제되어, B의 블로킹이 해제된다.
   - 인덱스가 이제 `13, 16, 26` 상태로 재정렬된 상태이므로, B는 새로운 간격인 `16~26` 구간에 `17`을 `INSERT`하고 `COMMIT`한다.

#### InnoDB의 상황별 락 동작 매커니즘 (REPEATABLE READ 기준)
- **단순 조회 (`SELECT`):** 
  - **MVCC(스냅샷) 기반으로 동작하기 때문에 락이 사용되지 않는다.**
  - 락 기반 매커니즘으로 동작하는 다른 DB들은, 앞서 말했듯 단순 조회 과정에서 공유 락을 사용한다.
  - 만약 MySQL에서도 명시적으로 공유 락을 사용하고 싶다면 `SELECT ... FOR SHARE` 명령어를 사용하면 된다.
- **데이터 변경 (`INSERT`, `UPDATE`, `DELETE`):**
  - **검색된 인덱스 구간에 배타 락이 사용**된다.
  - 만약 단순 조회에서도 명시적으로 배타 락을 사용하고 싶다면 `SELECT ... FOR UPDATE` 명령어를 사용하면 된다.

### 락의 생명주기와 데드락
#### 락의 생명주기 (2PL 프로토콜)
- 트랜잭션 내부에서 SQL 쿼리가 실행될 때 동적으로 획득된 **락은 트랜잭션이 완전히 `COMMIT`되거나 `ROLLBACK`되는 순간에 일괄적으로 함께 해제**된다.
- **트랜잭션 도중에 락이 해제되는 경우, 데이터 정합성이 깨질 수 있다.**

#### 데드락
- **복수의 트랜잭션이 서로가 점유하고 있는 락을 획득하기 위해 무한정 대기하는 상태**이다.
- InnoDB 엔진은 내부적으로 데드락을 감지하면 Undo Log를 참조하여 변경 사항이 적은 트랜잭션을 강제로 롤백시켜 데드락을 해제한다.

### 애플리케이션 레벨에서의 락과 DB 레벨에서의 락
#### 애플리케이션 레벨의 분산 락 (Redis)
- 선착순 예약 시스템에서 우리는 다중 서버들의 커넥션 풀이 고갈되지 않도록 Redis 기반 분산 락을 도입했다. 
- **이때 `락 획득 → 트랜잭션 시작 → 커넥션 획득 → 데이터 레코드 수정 → 트랜잭션 커밋 및 커넥션 반환 → 락 반환`의 순서를 거쳤는데, 여기서 획득한 락은 'Redis 기반 분산 락'이지 '실제 DB 엔진이 거는 락'이 아니다.**
- 즉, **커넥션을 획득하고 데이터 레코드를 수정하기에 앞서 DB 엔진이 내부적으로 배타 락을 걸게 되는데, 이 과정이 추상화된 것**이다.

#### DB 내부 락 (InnoDB 배타 락)
- **트랜잭션 진입 후 실제 SQL문이 실행되는 시점에, DB 엔진이 자체적으로 인덱스 레코드에 거는 락**이다.
- **커넥션 풀 고갈 방지 및 트래픽 제어가 목적인 분산 락과 달리, DB 내부 락은 데이터의 무결성 보장을 목적**으로 한다.

#### 전체 실행 흐름
1. **Redis 분산 락 획득:** 
   - 대다수 요청이 여기서 대기 또는 실패 처리
2. **DB 트랜잭션 시작 및 커넥션 획득**
3. **UPDATE 쿼리 등 SQL 실행:**
   - 이때 DB 엔진이 해당 인덱스 레코드에 배타 락 획득
4. **DB 트랜잭션 커밋 및 커넥션 반환:** 
   - 이때 DB 엔진이 배타 락을 일괄 해제
5. **Redis 분산 락 반환**
