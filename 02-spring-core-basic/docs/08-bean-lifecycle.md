## 스프링 빈의 생명주기(LifeCycle)와 콜백
### 초기화와 종료 작업의 필요성
> **애플리케이션이 시작될 때 미리 필요한 연결을 해두고, 종료될 때 안전하게 연결을 끊기 위해서는 객체의 초기화(Initialization)와 종료(Destruction) 작업이 필수적이다.**

#### DB 커넥션 풀
- 클라이언트 요청이 올 때마다 DB와 연결(TCP/IP 핸드쉐이킹 등)을 맺으면 응답 속도가 느려진다.
- 이를 해결하기 위해 애플리케이션 **서버가 뜰 때 DB와의 커넥션을 미리 여러 개(e.g. 10개, 100개) 맺어두고 풀(Pool)에 저장**해 둔다.
- 요청이 오면 풀에 있는 커넥션을 재활용하여 빠르게 응답할 수 있다.

#### 네트워크 소켓
- DB 커넥션과 마찬가지로, **서버가 뜰 때 외부 시스템과의 소켓을 미리 열어두면 요청 시점에 즉시 통신이 가능**하다.

### 스프링 빈의 이벤트 라이프사이클
> **스프링 컨테이너는 빈 객체 생성 및 DI 작업이 완료되면, 해당 빈에게 콜백 메서드를 통해 초기화 시점을 알려주고, 컨테이너가 종료되기 직전에도 소멸 콜백을 주어 안전하게 종료 작업을 할 수 있게 돕는다.**

#### 기본 라이프사이클 흐름
1. 스프링 컨테이너 생성
2. 스프링 빈 생성 (정확히는 **`BeanDefinition`이 먼저 등록되고, 이를 바탕으로 스프링 빈 생성**)
3. DI
4. 초기화 콜백 (빈이 사용될 준비가 완료된 시점)
5. 사용 (실제 애플리케이션 동작)
6. 소멸 전 콜백 (안전한 종료 작업 수행)
7. 스프링 종료

#### 생성자 주입에서는 빈 생성과 DI가 동시에 발생한다.
- Setter 주입이나 필드 주입은 객체 생성과 DI가 명확히 분리되어야 한다.
- 하지만 생성자 주입은 자바 언어의 특성상 `new 객체(의존성1, 의존성2)` 형태로 호출되어야 하므로, **스프링 빈 생성 단계에서 DI가 함께 처리**된다.

#### 초기화 작업의 시작 위치
> **초기화 작업은 객체가 완전히 생성되고, 필요한 값이 모두 세팅(DI)된 이후에 수행되어야 한다.**

- **빈이 아직 완전히 준비가 안 된 상황에서 초기화 작업을 수행하면 의도한 대로 결과가 동작하지 않을 수 있다.**
  - 예) DI 이전에 초기화(연결) 작업을 수행하는 경우
- 즉, 초기화 작업에서는 주입된 값을 사용해야 하는데, **빈 생성 단계(생성자 호출)에서 초기화를 수행하면 주입되지 않은 값을 사용하게 되므로** DI 이후에 초기화를 수행해야 한다.  

#### 스프링 빈 생명주기에서 초기화란 '초기화 콜백'을 의미한다.
> **변수 초기화에서의 초기화와는 완전히 다르다.**

- 앞서 확인한 기본 라이프사이클 흐름이 정확히는 **스프링 빈 생명주기 콜백**을 의미하고, 그 중에서도 DI가 끝난 후 호출되는 단계를 **초기화 콜백**이라고 부른다.
- 편의상 초기화 혹은 초기화 작업이라고 했지만, **변수가 아니라 스프링 빈을 초기화하는 작업**임을 기억하자.  

### 객체 생성과 초기화의 분리 원칙
> **객체의 인스턴스를 생성하는 작업(생성자)과 객체를 초기화하는 작업은 명확하게 분리하는 것이 좋다.** (유지보수와 설계 측면)

- **생성자의 책임(가벼운 작업):** 매개변수를 받고, 메모리를 할당하여 **객체를 생성하는 것에 집중**해야 한다.
- **초기화의 책임(무거운 작업):** **앞서 생성된 객체가** 외부 자원(DB, 네트워크 등)과 커넥션을 맺거나 연산을 수행하며 애플리케이션에서 **실제로 동작(사용)할 준비를 하는 역할을 전담**한다.
- **분리 시 장점: `lazyInit`**
  - 생성과 초기화를 분리해두면 객체는 미리 생성해두되, 초기화 작업은 객체가 최초로 사용되는 시점까지 지연(Lazy)시켜 시스템 자원을 효율적으로 사용할 수 있다.
  - 물론 초기화 작업이 무거워서 분리하는 것이기 때문에, 만약 가벼운 경우라면 생성자에서 처리해도 무방하다.

### 스프링 컨테이너의 `close()` 메서드
- 기본 AC 인터페이스는 컨테이너를 종료하는 `close()` 메서드를 제공하지 않는다.
  - 일반적인 애플리케이션 구동 중에는 개발자가 컨테이너를 직접 닫을 일이 없기 때문이다.
- 따라서 종료 라이프사이클 (소멸 전 콜백)을 테스트하는 등 **명시적으로 컨테이너를 닫아야 할 때는 `close()` 기능을 제공하는 하위 인터페이스나 구현체를 사용**해야 한다.
  - `ConfigurableApplicationContext`
  - `AnnotationConfigApplicationContext`

## 스프링 빈 생명주기 콜백
### 1. 인터페이스를 통한 초기화 (`InitializingBean`, `DisposableBean`)
> **초기의 방식으로, 빈 클래스에 인터페이스를 직접 구현하여 `afterPropertiesSet()`과 `destroy()` 메서드를 오버라이딩하는 방법**이다.

#### 단점
- **스프링 종속적:** 클래스가 스프링 전용 인터페이스(`InitializingBean`, `DisposableBean`)에 강하게 결합(의존)되어 버린다.
- **메서드명 변경 불가:** 오버라이딩했으므로 내가 원하는 이름으로 변경할 수 없다.
- **외부 라이브러리 적용 불가:**
  - 외부 라이브러리(AWS 클라이언트, 외부 DB 커넥션 풀 등)는 이미 빌드가 완료된 `.jar` 파일 형태로 제공된다.
  - 즉, 내가 **외부 라이브러리 소스코드를 열어서** `implements InitializingBean`과 같이 **직접 타이핑하여 수정할 수 없다**는 의미이다.

### 2. 설정 정보에 있는 @Bean 활용 (`@Bean(initMethod, destroyMethod)`)
> **설정 클래스(AppConfig)의 `@Bean` 어노테이션 속성에 초기화, 종료 메서드의 이름을 직접 지정하는 방식**이다.

#### 장점 및 특징
- **스프링 비의존적:** 
  - **빈으로 등록될 클래스(클라이언트 코드)에는 스프링 관련 코드가 아예 들어가지 않는다.**
  - 순수 자바 메서드만 만들어두고, 설정 파일에서 이름만 매칭해 주면 된다.
- **외부 라이브러리 적용 가능:**
  - 라이브러리 코드를 수정할 필요 없이, 해당 라이브러리 안에 이미 존재하는 초기화/종료 메서드의 이름만 지정해주면 되기 때문이다.
  - 즉, **설정 정보를 사용할 뿐이지 라이브러리 코드 자체는 있는 그대로 사용하면 되므로, 외부 라이브러리에도 적용이 가능**하다.
- **종료 메서드 자동 추론(`inferred`):**
  - `destoryMethod` 속성은 기본값이 `inferred`로 되어 있는데, 이는 **외부 라이브러리들이 관례로 많이 사용하는 종료 메서드 이름(`close`, `shutdown`)을 스프링이 알아서 추론하여 호출해 주는 것**을 의미한다.
  - 따라서 종료 메서드는 굳이 등록하지 않아도 된다.

### 3. 어노테이션 활용 (`@PostConstruct`, `@PreDestroy`)
> **초기화할 메서드와 종료할 메서드 위에 어노테이션(`@PostConstruct`, `@PreDestroy`)만 작성하면 된다.**

#### 장점
- **자바 표준 지원:** `jakarta.annotation.*`이기 때문에 **스프링이 아닌 다른 DI 컨테이너로 넘어가도 그대로 동작**한다.
- **컴포넌트 스캔과의 연계성:** 수동 등록(`@Bean`)하지 않고 자동 등록(`@Component`)하는 상황에서도 어노테이션만 붙이면 알아서 초기화 콜백/소멸 전 콜백이 실행된다.

#### 단점
- **외부 라이브러리 적용 불가:** 
  - '인터페이스를 통한 초기화'와 마찬가지이다.
  - 어노테이션을 붙여야 하므로 해당 클래스 소스코드를 수정할 수 있어야 한다.
  - 하지만 앞서 말했듯, **외부 라이브러리는 `.jar` 파일로 제공되기 때문에 소스코드를 열 수 없으므로** 어노테이션 또한 붙일 수 없다.

### 인텔리제이에서는 왜 `.class` 파일에서 소스코드를 확인할 수 있을까?
> **인텔리제이에는 디컴파일러가 내장되어 있기 때문이다.** 물론 그렇다고 해서, 코드를 수정할 수 있는 것은 아니다.

- `.class`(바이트코드) 파일은 `iconst`, `iadd` 같은 JVM 명령어(바이트코드)로 작성되어 있기 때문에, 직관적으로 읽을 수 없는 것이 정상이다.
- 하지만, **인텔리제이에서는 내부에 디컴파일러(Decompiler)가 내장되어 있어 바이트코드를 소스코드로 디컴파일하여 화면에 렌더링해준다.**
- 즉, 어디까지나 소스코드의 형태로 번역(디컴파일)만 해준 것이지, 수정할 수 없는 것은 동일하다.
