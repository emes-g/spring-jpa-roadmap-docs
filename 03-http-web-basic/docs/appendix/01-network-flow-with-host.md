## 네트워크 계층 모델
> OSI 7계층은 이론적인 표준 모델이고 **TCP/IP 4계층이 실제 구현체**이므로 **TCP/IP 4계층을 기준으로 통신 흐름을 이해하는 것이 좋다.**

### 계층 매핑 (TCP/IP 4계층 ↔ OSI 7계층)
- **애플리케이션 계층(L7, HTTP)** ↔ 응용, 표현, 세션 계층
- **전송 계층(L4, TCP)** ↔ 전송 계층
- **인터넷 계층(L3, IP)** ↔ 네트워크 계층
- **네트워크 인터페이스 계층(L2, MAC)** ↔ 데이터 링크, 물리 계층

### 네트워크 트래픽 처리 장비 (L2, L3, L4, L7)
- 실제 아키텍처는 TCP/IP 기반으로 동작하지만, 장비나 솔루션을 부를 때는 관행적으로 OSI 7계층의 번호를 차용한다.
  - 과거에는 HW 장비를 스위치, SW 장비를 로드밸런서라고 불렀지만 현재는 혼용해서 사용한다.
  - 중요한 것은 **장비명 앞에 붙은 수식어가 무엇(L2, L3, L4, L7)인가**이다.
- **상위 계층의 장비는 하위 계층의 장비를 포함**한다.
  - 상위 계층의 헤더를 보기 위해서는 하위 계층의 헤더부터 제거해야 하는데, 이때 **헤더에 적힌 정보가 버려지는 것이 아니라 (OS 커널에 의해) 상위 계층으로 함께 전달**된다.
  - L2: MAC 주소만 본다.
  - L3: IP 주소도 본다.
  - L4: PORT 번호도 본다.
  - L7: HTTP 메시지까지 전부 본다.
- 서버 애플리케이션(L7)에서 클라이언트의 IP 주소(`request.getRemoteAddr()`) 등을 가져올 수 있는 것도 전부 이러한 이유에서이다.

### NIC, MAC 주소, IP 주소
#### NIC(랜카드)
- 랜카드, 통신 모듈이라고도 한다.
- 랜카드(NIC)를 사용하는 이유는 **네트워크(인터넷)에 연결(접속)하기 위함**이다.
  - 유선 랜카드는 말그대로 **랜케이블(랜선)을 연결하여 네트워크에 접속**하는 것이고,
  - 무선 랜카드는 **와이파이같이 랜카드 주변의 일정 영역에서 랜케이블 없이도 네트워크를 사용**할 수 있게 해준다.
- 랜카드는 **기기가 네트워크에 연결(접속)할 수 있도록 변환기 역할**을 수행한다.
  - 디지털 데이터(0, 1)를 전송 매체의 특성에 맞게 물리적 신호(랜선은 전기 신호, 와이파이는 전파 신호)로 변환하여 내보내고,
  - 반대로 들어온 물리적 신호를 다시 데이터로 변환해 기기로 전달하는 것이다.

#### MAC 주소(물리적 주소)
- NIC에 부여되는 고유한 번호로, 제조사에서 만드는 NIC 자체에 부여하는 주소를 의미한다.
  - 예) `00-23-AE-D9-7A-9A`(앞에 6자리는 **OUI**라고 해서 제조사 고유 번호, 뒤에 6자리는 **기기 식별자**로 해당 기기의 일련번호를 의미함)
- 각 네트워크 장치가 **네트워크(서브넷) 내에서 다른 장치들과 구별될 수 있도록 해주는** 48비트의 식별 번호이다.
- 하지만 단순 식별 번호이기 때문에 **MAC 주소만으로는 기기가 어느 네트워크에 접속해 있는지를 파악할 수 없다.**
  - 즉, 인터넷 망의 라우터(중간 노드)들은 **MAC 주소만을 활용하여 목적지를 찾아가는(라우팅하는) 것은 불가능**하다. (어디로 가야할지 모르기 때문)    
- 따라서 라우터들은 **L3 계층에서 목적지 IP와 라우팅 테이블을 대조하여 행선지(다음 라우터, Next-hop)를 결정**하게 되는데, 이를 위해 **IP 주소도 필요**한 것이다.
  - 라우팅 테이블에는 목적지 IP 주소, Next-hop IP 주소(목적지 IP에 최적으로 가기 위해 다음에 가야 할 라우터의 IP 주소)가 존재한다. 

#### IP 주소(논리적 주소)
  - 기존에 IP 주소는 **네트워크 상에서 클라이언트와 서버가 통신하기 위해 필요한 주소**라고 정리했다.
    - 이는 상당 부분 추상화된 설명으로, MAC 주소에 대한 설명과 연계해 좀 더 깊이있게 알아보자.
  - **라우팅 테이블에서 IP 주소를 대조한 결과, 다음 라우터로 이동해야 한다**고 판단되면 다음과 같은 일이 발생한다.
    1. L3에서 ARP를 통해 Next-hop IP 주소를 MAC 주소로 변환하여, L2로 전달한다.
    2. L2에서는 현재 MAC 주소와 Next-hop MAC 주소를 헤더에 추가하고, 이를 이더넷 프레임으로 패키징해 다음 라우터(Next-hop)로 전송한다.
  - 굳이 MAC 주소로 변환해서 다음 라우터로 이동시키는 이유는, **네트워크 인터페이스 계층에서 이동할 때는 IP를 몰라서 MAC 주소 기준으로 이동**하기 때문이다.

## 기본적인 네트워크 통신 흐름
클라이언트(웹 브라우저)에서 출발한 데이터가 대상 서버에 도달하기까지, **네트워크 계층별로 목적지 정보를 획득하고 패키징 및 디패키징하는 일련의 과정**을 다룬다.

### 1. IP와 Port를 알아내는 시점 (클라이언트의 애플리케이션 계층)
> **클라이언트의 애플리케이션 계층에서 모든 목적지(대상 서버)의 정보(IP, PORT)가 식별**된다.

#### 1-1. PORT 번호 파악
- 사용자가 입력한 **URL의 `scheme`(프로토콜)을 분석**하여, 목적지(대상 서버의) PORT를 결정한다.
- `http://`인 경우에는 80, `https://`인 경우에는 443 

#### 1-2. IP 주소 획득 (DNS 조회)
- **TCP 연결(3-Way Handshake, 논리적 연결)을 수립하기 위해 대상 서버의 IP 주소가 필요**하므로, DNS 서버에 질의하여 IP 주소를 확보한다.

#### 1-3. HTTP 요청 메시지 생성
- 통신에 필요한 IP와 PORT 정보를 모두 확보한 후, 애플리케이션은 HTTP 요청 메시지를 생성한다.
- 이후 소켓 라이브러리를 통해 전송 계층(L4)에 요청 메시지를 전달할 때, **앞서 확보한 대상 서버의 정보(IP, PORT)를 함께 전달**한다.
- 참고로 **애플리케이션이 소켓 라이브러리를 통해 TCP 계층(OS 커널)으로 데이터를 밀어 넣는 것**은 **단순 함수 호출일 뿐, 네트워크 연결이 아니다.**

### 2. 패킷에 헤더를 추가하는 시점 (패키징 과정, 데이터 캡슐화)
> **애플리케이션은 대상 서버의 IP와 PORT를 알아내는 역할만 수행할 뿐, 실제 네트워크 전송 규격에 맞게 데이터를 캡슐화(헤더를 붙이는) 작업은 하위 계층에서 수행**된다.

#### 2-1. 전송 계층 (L4)
- 애플리케이션 계층이 전달한 목적지 PORT 번호와 출발지 PORT 번호, 전송 제어 정보, 패킷 순서 정보, 검증 정보 등을 담아 **TCP 헤더**를 생성한다.
- 이를 HTTP 메시지 앞에 붙여 **TCP 세그먼트**를 완성한다. 

#### 2-2. 인터넷 계층 (L3)
- 애플리케이션 계층이 전달한 목적지 IP 주소와 출발지 IP 주소 등을 담아 **IP 헤더**를 생성한다.
- 이를 TCP 세그먼트 앞에 붙여 **IP 패킷**을 완성한다.

#### 2-3. 네트워크 인터페이스 계층 (L2)
- 완성된 **IP 패킷에 물리적 주소(MAC) 정보가 담긴 이더넷 프레임을 씌워 실제 인터넷 망(광케이블 등)으로 송출**한다. 

### 3. 인터넷 망을 거치는 시점 (Next-hop 라우팅)
> **패킷은 중간 노드의 네트워크 인터페이스 계층만을 거쳐 대상 서버로 가는 것이 아니다.**
 
- 중간 노드(라우터)에 전기 신호가 도착하면, L2 계층에서 이더넷 프레임(MAC 주소 컨테이너)을 뜯어낸 후 패킷을 L3 계층으로 올린다.
- **L3 계층에서 목적지 IP와 라우팅 테이블을 대조하여 다음 목적지를 결정**하면, 다시 하위의 L2 계층으로 내려보내 새로운 이더넷 프레임을 씌워 송출한다.
  - 참고로 이더넷 프레임은 IP 패킷에 이더넷 헤더를 붙여 생성한 것이며, **이더넷 헤더에는 현재 라우터의 MAC 주소와 다음 라우터의 MAC 주소가 담겨 있다.** 
- 즉, **패킷은 최종 서버에 도착할 때까지 L2와 L3 계층을 수차례 거치며 전송**된다.

### 4. 대상 서버 도착 후의 디패키징 과정
> **인터넷 망을 거친 패킷이 대상 서버(프록시 서버)의 네트워크 인터페이스(L2)에 도착하면, 클라이언트의 캡슐화 과정을 역순으로 거치며 디패키징**된다.

#### 4-1. 인터넷 계층 (L3)
- **수신된 패킷의 목적지 IP가 자신의 IP인(현재 라우터의 IP와 동일한) 경우**, IP 헤더를 제거하고 상위 계층으로 올린다.
  - 대상 서버(최종 목적지)에 도달하여 더 이상 라우팅 테이블을 대조할 필요가 없는 경우이다.
  - 만약 대상 서버가 아니었다면, 라우팅 테이블을 대조하여 다음 목적지를 결정했을텐데 이를 **Next-hop 라우팅**이라고 한다.

#### 4-2. 전송 계층 (L4)
- 수신된 세그먼트의 목적지 PORT를 확인하고 TCP 헤더를 제거한다.
- 이후 **해당 PORT를 열고 대기(Listen) 중인 애플리케이션 프로세스(서버)로 원본 데이터를 밀어 올린다.**

#### 4-3. 애플리케이션 계층 (L7)
- 대상 서버(의 프록시 애플리케이션)는 **이미 하위 계층에서 모두 디패키징된, 순수한 HTTP 요청 메시지를 수신하여 읽게 된다.**

## 서버 인프라의 물리적/논리적 구조
인터넷(네트워크) 망을 거쳐 대상 장비의 랜카드(NIC)에 도달한 데이터가, **장비 내부에서 어떻게 정확한 목적지(애플리케이션)을 찾아가는지**, 그리고 **트래픽 규모에 따라 서버 인프라가 어떻게 확장되는지**를 다룬다.

### 물리적 서버와 논리적 서버
- **물리적 서버(HW):**
  - CPU, 메모리, 랜카드(NIC)를 갖춘 하나의 **컴퓨터 장비 본체**(Host)를 의미한다.
- **논리적 서버(SW):**
  - **물리적 장비의 OS 위에서 구동되는 프로세스**(nginx, tomcat, spring boot, ...)을 의미한다.
  - 프로세스란 말에서 알 수 있듯, 이들은 **각각 독립적인 메모리 공간을 할당받아 실행 중**이다.
  - 내부 서버, 애플리케이션, 프로세스 등 다양하게 불린다.

### 애플리케이션 식별 기준 (PORT)
> **IP 주소를 통해 대상 서버까지 찾아왔다면, 서버 내부에서 어떤 애플리케이션에게 데이터를 전달할지는 PORT 번호가 결정**한다.

- 하나의 OS에서는 0번부터 65535번 포트까지 사용할 수 있다.
  - 0번부터 1023번 포트까지는 **Well-Known Port**라고 해서 용도 별로 예약되어 있다. (마칙 예약어처럼)
- 각 애플리케이션은 **구동될 때 특정 포트 하나를 독점하여 점유**(Listen)한다.
- TCP 계층(OS의 네트워크 스택)은 **패킷의 포트 번호를 확인하여, 해당 포트를 점유하고 있는 프로세스에게 정확히 데이터를 밀어 넣는다.**

### MAC, IP, PORT 간단 요약
#### MAC 주소 (L2 계층)
> **인접한 장비로 프레임을 전송하기 위해 사용되는 물리적 주소**

- 라우터를 거칠 때마다 갱신되며, L2 계층에서의 이동을 위해 사용된다.

#### IP 주소 (L3 계층)
> **대상 서버를 식별하기 위한 논리적 주소**

- L2 계층에서의 이동을 위해서는, **L3 계층에서 인접한 장비의 IP를 확인하고, ARP를 통해 MAC 주소로 변환하여 L2 계층에 전달**해야 한다.

#### PORT 번호 (L4 계층)
> **대상 서버의 OS 내에서 실행 중인 여러 프로그램 중, 실제 데이터를 전달받을 대상을 식별하는 번호**

### 단일 서버 환경 구조
> **트래픽 규모가 크지 않을 때 구축**하는 가장 기본적인 아키텍처로, **물리적 장비 1대에 모든 서버(애플리케이션)를 구동**하는 형태이다.

#### 물리/논리적 구조
- **기기 1대, 1개의 공인 IP**, 다수의 PORT

#### 공인 IP(Public IP)
- 외부 인터넷 망에서 클라이언트가 직접 찾아올 수 있도록 **전 세계에 유일하게 할당된 단 1개의 IP 주소**이다.
- 단일 서버는 외부와의 통신을 위해 이 공인 IP 하나만을 사용한다.

#### 동작 흐름
1. 클라이언트가 공인 IP의 80/443 포트로 접속하면, 해당 포트를 점유하고 있는 리버스 프록시(Nginx)가 요청을 수신한다.
2. **프록시는 요청을 분석(라우팅)하여, 같은 기기 내부에서 다른 포트를 점유하고 있는 내부 애플리케이션으로 데이터를 전달(포워딩)한다.**

### 다중 서버 환경 구조
> **서비스 규모가 커져 트래픽이 증가하면, 1대의 물리적 장비(CPU/메모리)로는 감당할 수 없게 되는데, 이때 Scale-out 방식을 적용**한다.

- Scale-out은 **동일한 역할을 수행하는 물리적 장비를 여러 대 사용하여 트래픽을 분산시키는 것**를 의미한다.

#### 물리/논리적 구조
- **기기 여러 대, 여러 개의 IP**, 다수의 PORT

#### IP의 역할 분리 (공인 IP vs 사설 IP)
- 인터넷 망을 통해 클라이언트와 직접적으로 연결되는(가장 앞단의) **리버스 프록시 장비에만 공인 IP를 부여**한다.
- 뒷단에 배치된 실제 비즈니스 로직 처리 장비들(WAS)은 **외부망과 직접 통신할 필요가 없고 보안이 중요하므로, 내부망에서만 식별 가능한 사설 IP(`10.0.0.2`, `192.168.1.10` 등)를 각각 별도로 할당**받는다.

#### 리버스 프록시와 로드 밸런싱
- 목적지 장비(다중 서버 환경에서는 사설 IP)가 여러 개로 늘어났으므로, **트래픽을 골고루 분배해 줄 역할이 필요해진다.**
- **리버스 프록시(Nginx 등)는 대개 트래픽을 분산시키는 로드밸런싱 기능을 내장**하고 있기 때문에, 로드밸런서의 역할도 겸용한다고 볼 수 있다.

#### MSA 아키텍처에서의 다중화 (Gateway Scale-out)
> **MSA 환경(`nginx → gateway → auth/stats/...`)에서 Scale-out을 진행할 때, 최종 목적지뿐만 아니라 중간의 Gateway 역시 반드시 여러 대로 다중화**해야 한다.    
 
- **트래픽 병목(Bottleneck) 현상 방지:**
  - 모든 트래픽이 통과하는 유일한 출입구가 Gateway 1대뿐이라면, 뒷단(실제 비즈니스 로직을 처리하는) 서버를 아무리 늘려도 Gateway의 처리 한계치에서 병목이 발생하기 때문이다.
- **단일 장애점(SPOF) 방지:**
  - 유일한 Gateway 장비가 다운되면, 뒷단 서버들이 정상이어도 서비스 전체가 마비되기 때문이다.
- **자체적인 연산의 부하 분산:**
  - Gateway는 단순히 뒷단의 서버로 요청을 포워딩(전달)하는 것이 아니다.
  - **라우팅 검사, 인증(JWT) 등 CPU 연산도 수행하므로 자체적인 부하 분산 역시 필요**하다.

#### 동작 흐름
1. 가장 앞단의 리버스 프록시(Nginx) 장비가 공인 IP를 통해 외부 트래픽을 수신한다. 
2. **프록시는 내장된 로드밸런싱 알고리즘에 따라 목적지를 결정**한 뒤, **포트 단위가 아닌 완전히 독립된 사설 IP를 가진 개별 물리적 장비(WAS1, WAS2 등) 중 한 곳으로 요청을 포워딩**한다.
   - 만약 MSA 구조였다면, 여러 대의 Gateway 장비(사설 IP) 중 한 곳으로 1차 포워딩을 수행하고,
   - 요청을 받은 Gateway 장비에서 다시 로드밸런싱을 통해, 최종 목적지 장비(Auth1, Auth2, Stats1, Stats2, ...) 중 한 곳으로 2차 포워딩을 수행한다.

## 프록시 라우팅과 데이터의 표현
### 프록시
> 프록시는 **클라이언트와 서버 사이에서 트래픽을 대신 받아 전달해 주는 '대리인' 역할**을 한다.

- 이 프록시가 **네트워크의 어느 쪽에 더 가깝게 위치하여 누구를 보호하느냐**에 따라 두 가지로 구분된다.

#### 포워드 프록시 (Forward Proxy)
> **클라이언트 측 네트워크에 위치하여, 밖으로 나가는 '아웃바운드 트래픽'을 처리**한다.

- 주로 **기업의 사내망에서 외부 인터넷으로 접속할 때** 거치게 되며, **특정 유해 사이트 접근을 차단**하거나 **자주 가는 사이트의 데이터를 캐싱하는 것**이 주 목적이다.
  - 즉, **인터넷 망 앞단(네트워크 망을 거친 후)에 위치하는 프록시**이다.
- 서버 입장에서는 **진짜 클라이언트의 IP가 무엇인지 알 수 없고**, 오직 포워드 프록시의 IP만 보인다. (**클라이언트를 숨겨줌**)

#### 리버스 프록시 (Reverse Proxy)
> **서버 측 네트워크에 위치하여, 외부 인터넷에서 들어오는 '인바운드 트래픽'을 최초로 수신**한다.

- **인터넷 망 뒷단(네트워크 망을 거친 후)에 위치하는 프록시**로, **들어온 트래픽을 로드밸런싱**(여러 대의 내부 서버로 분산)한다.
- 클라이언트 입장에서는 **뒤에 어떤 내부 서버들이 몇 대나 있는지 알 수 없으며**, 오직 리버스 프록시와만 통신한다고 생각하게 된다. (**서버를 숨겨줌**)

### 공인/사설 IP vs 가상/실제 IP
공인 IP를 VIP(가상 IP)와 사설 IP를 RIP(실제 IP)와 동일시하여 이해할 수 있는데, **이 둘은 분류하는 기준과 목적이 전혀 다른 독립적인 개념**이다.

#### 공인/사설 IP (네트워크 위치 기준)
> **인터넷 망과 직접 통신할 수 있는지 여부**를 나타내는 절대적인 속성이다.

- **공인 IP:** 외부 인터넷에서 직접 접속할 수 있는 IP
- **사설 IP:** 외부 인터넷과 단절된 내부망 안에서만 통신할 수 있는 IP

#### 가상/실제 IP (트래픽 분산 역할 기준)
> **로드밸런싱 환경에서 통신하는 구간에 따라 장비가 어떤 상대적인 역할을 하는지** 나타낸다. 

- **가상 IP(Virtual IP, VIP):** 특정 통신 구간에서 **클라이언트의 트래픽을 일괄적으로 받아내기 위해 로드밸런서나 프록시가 노출하는 단일 대표 IP**
- **실제 IP(Real IP, RIP):** 특정 통신 구간에서 로드밸런서 뒷단에 위치하여, **로드밸런서로부터 트래픽을 분배받는 장비의 IP**

#### 두 개념이 1:1로 동일하지 않은 이유 (위치와 상대성의 차이)
> **공인/사설 IP는 네트워크 접속 위치에 따른 절대적(불변) 주소인 반면, VIP/RIP는 통신 구간에 따른 상대적 주소이기 때문이다.** 

- 일반적인 단일 프록시 구조에서는 가장 앞단의 장비(Nginx)가 외부 통신을 위해 공인 IP를 할당받는 동시에, 뒤에 있는 서버들로 트래픽을 분산하는 대표 역할을 하므로 VIP가 된다.
- 이러한 상황 때문에 공인 IP와 VIP가 같은 것이라고 착각하게 되는데, **실제로 VIP와 RIP는 네트워크 위치(공인/사설)와 무관하며, 통신 구간에 따라 변하는 상대적인 개념**이다.
- **사설 IP이면서 VIP인 경우:**
  - 외부 인터넷과 단절된 내부망(사설 IP 대역) 안에서도 서버의 부하를 분산하기 위해 내부용 로드밸런서를 둘 수 있다.
  - 이때 트래픽을 받기 위해 노출하는 대표 주소(VIP)는 공인 IP가 아닌 사설 IP가 된다.
- **RIP이자 VIP인 경우:**
  - MSA 환경(`nginx → gateway → auth/stats/...`)에서 중간에 위치한 Gateway는 Nginx 입장에서는 RIP가 되지만, 트래픽을 넘겨받는 뒷단의 Auth 서버들 입장에서는 로드밸런서이므로 VIP가 된다.

### 가상 호스팅
> **단일 프록시 장비(1개의 VIP)가 외부의 모든 트래픽을 수신한 뒤, 요청된 논리적 도메인이나 경로에 따라 내부의 여러 목적지 그룹으로 트래픽을 분배하여 처리하는 기술**이다.
 
- Nginx에서는 이를 `server` 블록(가상 서버)과 `upstream` 블록(RIP 목적지 그룹)을 통해 구현한다.

#### Nginx 설정 예시
```nginx
http {
    # 1. 목적지 그룹 정의 (upstream)
    # 로드밸런싱 대상이 되는 뒷단 장비들의 사설 IP(RIP) 그룹 정의
    upstream api_cluster {
        server 192.168.1.11:8080;
        server 192.168.1.12:8080;
    }

    # 2. 가상 서버 정의 (server)
    server {
        listen 80;
        server_name api.test.com;

        location / {
            # 3. 포워딩 (Reverse Proxy)
            # api.test.com:80으로 들어온 요청을 위에서 정의한 'api_cluster' 그룹으로 포워딩(전달)
            proxy_pass http://api_cluster;

            # 4. 헤더 보존 (IP 및 도메인 추적)
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}
```
- 현재는 `server_name admin.test.com;`을 담당하는 `server` 블록이 없기 때문에 Nginx는 이 요청을 어디로 포워딩해야 할지 모른다.
- 따라서 트래픽을 버리거나 Nginx의 기본 에러 페이지를 반환하게 된다.

#### Nginx 설정에서 헤더 보존의 필요성
- 클라이언트의 요청이 프록시 장비를 거쳐 내부 서버(RIP)로 전달되면, **내부 서버가 인식하는 통신의 출발지 IP는 클라이언트의 IP가 아니라 프록시 장비의 IP로 변경**된다.
- 따라서 **실제 클라이언트의 원래 IP와 최초 요청 도메인을 내부 서버에서도 식별할 수 있도록, 프록시 장비에서 포워딩을 수행할 때 `X-Real-IP`, `X-Forwarded-For`, `Host` 헤더에 원본 데이터를 명시적으로 담아 전달**해야 한다.

### Host 헤더를 통한 L7 라우팅
#### 개요
- L3 계층의 IP 주소와 L4 계층의 PORT 번호만으로는 프록시 서버 내부에 설정된 여러 애플리케이션(도메인) 중 정확한 목적지를 식별할 수 없다.
- **프록시 장비에 트래픽이 도달한 이후, 내부의 어떤 서비스로 라우팅할지 결정하는 최종 기준**은 HTTP 요청 메시지의 `Host` 헤더이다.

#### 식별의 한계와 Host 헤더의 역할
- 클라이언트가 DNS를 통해 알아내어 접속하는 IP는 실제 백엔드 서버가 아닌, 가장 앞단 프록시 장비의 공인 IP이다.
- 프록시 장비 1대는 가상 호스팅 기술을 통해 여러 도메인(`api.test.com`, `admin.test.com`)의 트래픽을 동시에 수용한다.
- TCP 연결이 수립된 후, Nginx는 전달받은 HTTP 요청(L7)의 헤더 값을 분석한다.
- 내부에 설정된 여러 가상 서버(`server` 블록) 중, `server_name`이 이 Host 헤더 값과 일치하는 곳으로 트래픽을 라우팅(포워딩)한다.

#### 가상 서버 (`server` 블록)
> **하나의 물리적인 프록시 장비(VIP) 내부에 생성된 논리적인 라우팅 단위**이다.

- 클라이언트가 VIP로 접속했을 때, 어떤 도메인으로 들어왔느냐에 따라 적절한 목적지 그룹(`upstream` 블록)으로 트래픽을 토스해 주는 역할을 한다.
  - 예1) Host 헤더의 값(도메인)이 `api.test.com`인 경우 → `api_cluster` 그룹으로 포워딩
  - 예2) Host 헤더의 값(도메인)이 `admin.test.com`인 경우 → `admin_cluster` 그룹으로 포워딩
- 말그대로, 가상 서버는 **해당 VIP를 가진 프록시 장비 내 가상으로(논리적으로) 존재하는 서버로, 적절한 `upstream`으로 호스팅해주기 위한 서버**라고 이해할 수 있다. 

#### Nginx 설정 예시 (여러 도메인으로 호스팅하는 경우)
```nginx
http {
    # 목적지 그룹들 (RIP 모음)
    upstream api_cluster { ... }
    upstream admin_cluster { ... }

    # 1. api.test.com 트래픽을 담당하는 가상 서버
    server {
        listen 80;
        server_name api.test.com;
        location / {
            proxy_pass http://api_cluster;
        }
    }

    # 2. admin.test.com 트래픽을 담당하는 가상 서버
    server {
        listen 80;
        server_name admin.test.com;
        location / {
            proxy_pass http://admin_cluster;
        }
    }
}
```

### HTTPS 환경에서의 라우팅 한계와 SNI
**현대의 웹 통신은 대부분 데이터가 암호화되는 HTTPS를 기반**으로 하는데, HTTP 통신에서와 달리 **HTTPS 통신에서는 Host 헤더를 읽지 못해 클라이언트-서버 연결을 수립할 수 없는 문제가 발생**한다.

#### 암호화 통신의 구조적 모순 (TLS Handshake와 Host 헤더)
> **도메인(Host)을 알아야 적절한 인증서를 제공할 수 있는데, 인증서를 제공하여 암호화 연결을 수립하기 전까지는 도메인을 읽을 수 없는 교착 상태(Deadlock)에 빠지게 된다.**
- 프록시 장비(Nginx) 1대가 여러 도메인(`api.test.com`, `admin.test.com` 등)을 동시에 호스팅하는 상황을 가정하자.
- 클라이언트가 HTTPS로 접속을 시도하면, 데이터를 주고받기 전 암호화 연결(TLS Handshake)을 먼저 수립해야 하며, 이때 서버는 클라이언트가 요청한 도메인(Host)에 맞는 'SSL/TLS 인증서'를 제공해야 한다.
- **하지만 클라이언트가 요청한 목적지 도메인이 적힌 `Host` 헤더는 HTTP 데이터(L7) 안에 포함되어 있으므로 읽을 수 없다.** (암호화 연결이 수립된 후에야 복호화해서 읽을 수 있다.)

#### SNI (Server Name Indication)
- SNI는 이를 해결하기 위해 등장한 TLS 프로토콜의 확장 기술이다.
- 클라이언트가 암호화 연결을 시작하기 위해 **서버에 보내는 최초의 메시지(`Client Hello`)에, 자신이 접속하고자 하는 목적지 도메인의 이름(`api.test.com`)을 암호화하지 않은 평문(Plaintext)으로 덧붙여서 전송**한다.
- 서버(프록시 장비)는 이 평문 정보를 읽고 클라이언트의 목적지 도메인을 파악한 뒤, 그에 맞는 올바른 인증서(SSL/TLS 인증서)를 반환하여 암호화 연결(TLS Handshake)를 무사히 수립한다.

### SSL/TLS
#### SSL/TLS (표준 보안 프로토콜)
- 클라이언트와 서버 간에 주고받는 데이터를 암호화하는 표준 보안 프로토콜(통신 규약)이다.
- HTTPS 통신의 기반(HTTPS 통신을 가능하게 하는 핵심) 기술이다.

#### SSL/TLS 인증서 (전자 문서)
- 서버가 자신의 신원을 증명하기 위해 클라이언트에게 제공하는 데이터(전자 문서)다.
- 암호화 통신을 시작하기 전, 다음 2가지 핵심 역할을 수행한다.
  - **신원 증명:** **신뢰할 수 있는 제3자(CA, 인증기관)의 서명이 포함된 문서를 통해, 해당 서버가 위조되지 않은 진짜 도메인의 서버임을 보증**한다.
  - **공개키 전달:** **통신 데이터 암호화에 필요한 서버의 공개키를 클라이언트에게 전달**한다.

### 인코딩
> **전송/저장 등을 위해 데이터를 적절한 형태로 변환하는 것**을 말한다. 

- 데이터를 시스템에 저장하거나 네트워크로 전송하기 위해, 합의된 규칙에 따라 적절한 형태(포맷)으로 변환하는 과정을 **인코딩**이라고 한다.
- 반대로, 변환된 데이터를 원래의 상태로 복원하는 과정은 **디코딩**이라고 한다.

#### 통신에서의 문자 인코딩 (Character Encoding)
> **HTTP 요청이나 응답 데이터(L7)에 담긴 텍스트 역시 네트워크를 통해 전송되려면 비트(0과 1의 이진 데이터) 스트림, 즉 바이트(Byte) 배열 형태로 변환되어야 한다.**

- 문자를 바이트 배열로 변환하기 위해서는 '문자 집합(**어떤 문자에 어떤 번호를 매길 것인가**)'과 '인코딩(**그 번호를 어떻게 바이트로 변환할 것인가**)'이라는 두 가지 개념을 모두 고려하고 적용해야 한다.
- **아스키코드 (ASCII):**
  - 초기에 영문 알파벳과 숫자, 일부 특수문자를 표현하기 위해 만들어진 7비트 규격이다.
  - 문자에 번호를 매기는 **문자 집합인 동시에**, 그 번호를 그대로 1바이트 크기로 변환하는 **인코딩 규격**이기도 하다.
  - 한글 등 **타 국가의 문자를 표현할 수 없는 한계**가 있다.
- **유니코드 (Unicode):**
  - 아스키코드의 한계를 극복하기 위해 등장한 **국제 표준 문자 집합**이다.
  - 전 세계의 모든 문자에 일관된 고유 번호('가' → `U+AC00`)를 맵핑한 논리적인 표이며, **물리적인 변환 규칙(인코딩 규격) 자체는 아니다.**
- **UTF-8:**
  - **유니코드 문자 집합의 번호들을 실제 바이트 데이터로 변환하는 대표적인 가변 길이 인코딩 규격**이다.
  - 이때 가변 길이 인코딩 규격이라 불리는 이유는 **영문은 1바이트, 한글은 3바이트 등으로 길이를 가변적으로 처리하여 데이터 크기를 효율적으로 관리하기 때문**이다.
  - 현대 웹 통신(HTTP) 및 대부분의 시스템 환경에서 **데이터 깨짐을 방지하기 위한 기본 표준으로 활용**되고 있다.
