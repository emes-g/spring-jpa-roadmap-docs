## 영속성 컨텍스트
### EntityManager와 영속성 컨텍스트
#### EntityManager
- 이름에서 알 수 있듯, **엔티티(DB 테이블과 매핑된 자바 객체)의 저장/수정/조회/삭제를 관리하는 객체**이다.
- **사용자의 요청(스레드)이 발생할 때마다 생성**되며, DB 커넥션을 사용하여 DB에 접근한다.
- 동시성 문제가 발생하므로 스레드 간 공유해서는 안 된다.

#### 영속성 컨텍스트 (Persistence Context)
- **애플리케이션과 DB 사이에서 엔티티를 영구적으로 저장하고 관리하는 가상의(논리적인) 공간**이다.
- **트랜잭션이 시작될 때 `EntityManager`와 1:1로 매핑되어 독립적으로 생성**되며, **트랜잭션 종료 시 함께 소멸**된다.
- **JPA의 핵심 동작은 `EntityManager`를 기반으로 수행**되며, **`TransactionManager`는 `EntityManager`의 생명주기를 오케스트레이션하는 역할을 수행**한다.
  - `@Transactional`을 등록하면 내부적으로 `TransactionManager`가 동작하여, DB 트랜잭션을 시작하고 `EntityManager`를 할당해 준다.
  - 시작 시점뿐만 아니라 트랜잭션 커밋/롤백 시점에도 마찬가지로 `TransactionManager`가 동작한다.

### 엔티티의 상태
#### 비영속 (New/Transient)
- 영속성 컨텍스트와 전혀 관계가 없는 **순수한 객체 상태**이다. (POJO)

#### 영속 (Managed)
- **영속성 컨텍스트에 의해 관리되는 상태**이다.

#### 준영속 (Detached)
- 영속성 컨텍스트에 저장되었다가 분리되어, **더 이상 (JPA로부터) 관리받지 않는 상태**이다.

#### 삭제 (Removed)
- 삭제된 상태이다.

### 영속성 컨텍스트의 핵심 이점
#### 1차 캐시 (First-level Cache)
- **영속성 컨텍스트 내부에는 PK를 Key로, 엔티티 객체를 Value로 가지는 Map 형태의 1차 캐시(`Map<PK, Entity>`)가 존재**한다.
- **엔티티를 조회할 때는 DB에 앞서 1차 캐시를 먼저 탐색**한다.
  - 데이터가 존재하면 객체를 바로 반환한다.
  - 없으면 DB에서 조회 후 캐싱한 뒤 반환한다.

#### 동일성 보장 (Identity Guarantee)
- **같은 트랜잭션 내에서 동일한 레코드를 조회하면 메모리 주소까지 동일한 하나의 객체가 반환됨을 보장**하는 성질이다.
- **자바 컬렉션에서 동일한 요소를 두 번 꺼내면 참조값이 같은 동일한 객체가 반환**되는 것처럼, **영속성 컨텍스트에서 역시 동일한 레코드를 두 번 조회하면 동일한 객체(엔티티)를 획득**할 수 있다.
- **영속성 컨텍스트에서 데이터를 조회할 때, 어떤 컬럼으로 조회하든 내부적으로 PK를 사용**하게 된다.
  - 가령 `JPQL`을 사용해서 조건절로 데이터를 조회했다고 치자.
  - 1차 캐시는 PK를 Key로 가지고 있기 때문에 사용할 수 없어서, 우선적으로 DB를 조회하게 된다.
  - DB에서 결과 레코드를 가져온 뒤 해당 레코드의 PK 값을 확인하고, 1차 캐시에 동일한 PK를 가진 객체가 있는지 검사한다.
  - 1차 캐시에 이미 존재하는 엔티티였다면, 방금 DB에서 가져온 엔티티는 버리고 기존 1차 캐시에 있던 객체의 참조를 반환하여 동일성을 보장한다.
- **동일성 보장의 목적:**
  - **상태 동기화 충돌을 차단**하는 것이 목적이다.
  - 가령 동일성이 보장되지 않아 같은 레코드를 가리키는 복수의 객체가 생성 및 수정(`member1.setAge(20)`, `member2.setAge(30)`)되었다고 하자.
  - 트랜잭션을 커밋할 때 영속성 컨텍스트 안의 모든 엔티티와 스냅샷을 비교하여 `UPDATE` 커맨드를 생성해야 하는데, JPA는 어떤 데이터의 상태가 진짜(Source of Truth)인지 알 수 있는 방법이 없다.
  - 결론적으로, 이러한 상태 동기화 충돌을 방지하기 위해 동일성은 보장되어야 한다.

#### 트랜잭션을 지원하는 쓰기 지연 (Transactional Write-Behind)
- **엔티티에 쓰기 작업이 발생해도 즉시 DB에 쿼리를 전송하지 않고, '쓰기 지연 SQL 저장소'에 쿼리를 대기시켰다가 트랜잭션 커밋 시점(`flush`)에 일괄 전송**하여 통신 횟수를 최적화한다.
- **작업별 쿼리 생성 및 적재 시점:**
  - **추가(`INSERT`) 및 삭제(`DELETE`):**
    - `em.persist()`, `em.remove()` 등 **메서드를 호출하는 그 즉시 쿼리가 생성되어 쓰기 지연 SQL 저장소에 쌓인다.**
  - **수정(`UPDATE`):**
    - 자바 객체의 값을 변경(`setter` 호출 등)하는 시점에는 쿼리가 생성되지 않으며, 저장소에도 쌓이지 않는다.
    - 오직 **트랜잭션 커밋(`flush`) 시점에 변경 감지(Dirty Checking)을 통해서만 쿼리가 생성**된다. 

#### 변경 감지 (Dirty Checking)
- **엔티티의 데이터를 수정할 때 명시적인 `update()` 호출 없이, 객체의 값만 변경해도 자동으로 DB에 반영**되는 기능이다.
- **동작 원리 및 시점:**
  - 앞서 말했듯, 객체의 값이 변경될 때마다 쿼리가 생성되는 것이 아니다.
  - 엔티티를 영속성 컨텍스트에 최초로 저장(또는 조회)할 때 스냅샷을 보관해두고, 트랜잭션 커밋으로 인해 `flush`가 발생하는 순간에 스냅샷과 현재 엔티티 객체의 상태를 비교한다.
  - 두 상태가 다르다면, 현재 엔티티 객체의 상태를 반영하기 위해 `UPDATE` 쿼리를 생성하여 쓰기 지연 SQL 저장소에 적재한다.

### 트랜잭션 커밋 시의 내부 동작
1. **`flush` 호출:**
   - 영속성 컨텍스트의 변경 내용을 DB에 동기화하는 작업이 시작된다.
2. **변경 감지 (Dirty Checking):**
   - 영속성 컨텍스트 내의 모든 엔티티에 대해서, 해당 엔티티의 현재 상태와 최초 스냅샷을 비교한다.
3. **`UPDATE` 쿼리 생성 및 적재:**
   - 변경된 엔티티에 대한 `UPDATE` 쿼리를 생성하여 쓰기 지연 SQL 저장소에 넣는다.
4. **DB로 일괄 전송**
   - 쓰기 지연 SQL 저장소에 모여있던 모든 쿼리(`INSERT`, `UPDATE`, `DELETE`)를 DB로 전송한다.
   - 실제로 데이터를 변경하는 시점이기 때문에 이때 내부적으로 인덱스 레코드에 락을 걸게 된다.
5. **DB 커밋:**
   - DB 트랜잭션을 커밋하여 작업을 확정한다.
   - 트랜잭션 커밋 시점에 획득했던 락들도 일괄적으로 해제된다.

## 프록시와 연관관계 로딩 전략
### 프록시(Proxy) 객체
- **JPA가 DB 조회를 최대한 미루기 위해 사용하는 가짜 객체**다.
- **실제 엔티티 클래스를 상속**받아 만들어지며, **내부에는 실제 데이터 대신 실제 객체를 가리키는 참조**(Target)를 가진다.
- 프록시 객체의 **실제 데이터에 최초로 접근할 때 영속성 컨텍스트에 초기화를 요청하여 DB에서 실제 데이터를 가져온다.**

### 연관관계 로딩 전략
> **엔티티 내부에 연관된 다른 엔티티가 존재할 때, 그 연관된 데이터를 DB에서 언제 가져올지 결정하는 전략**이다.

#### 즉시 로딩 (`FetchType.EAGER`)
- 엔티티를 조회할 때, **연관된 엔티티도 그 시점에 한꺼번에서 DB에서 조회**해 온다.
- 즉시 로딩 방식에서도 후술할 N+1 문제가 발생할 수는 있지만, 이는 애플리케이션 레벨에서 해결할 수 있다. 

#### 지연 로딩 (`FetchType.LAZY`)
- 엔티티를 조회할 때, **연관된 엔티티는 실제 데이터 대신 프록시 객체로** 채워 넣는다.
- 이후 해당 프록시 객체의 실제 데이터가 필요한 시점(사용되는 시점)에 영속성 컨텍스트에 요청하여 실제 데이터를 가져온다.

### N+1 문제의 발생 원리와 JPQL의 한계
#### N+1 문제
- **단일 쿼리 1번으로 N개의 결과 레코드가 반환된 상황에서, 그 N개의 레코드 각각에 대해서 연관된 데이터를 채우기 위해 추가 쿼리가 발생하는 문제**를 말한다.
- 즉, **쿼리를 1번 수행하려고 했는데, 내부적으로 쿼리가 N+1번 발생하게 되는 문제**를 의미한다.

#### 동작 방식 비교 (`em.find` vs JPQL)
- JPA에서 기본적으로 제공하는 `em.find()`와 달리, **JPQL의 경우 엔티티의 로딩 전략을 사전에 고려하지 않기 때문에 의도치 않게 N+1 문제가 발생할 확률이 더 높다.** 
- 아래는 `Member`와 `Team`이 즉시 로딩(`EAGER`)으로 설정된 상황에서 JPA와 JPQL의 동작을 비교해보는 예시이다.
- **단건 조회 | `em.find(Member.class, 1L)`:**
  - **JPA는 쿼리를 생성하기 전에 엔티티의 로딩 전략을 미리 확인**한다.
  - 엔티티의 로딩 전략이 `EAGER`인 경우, 처음부터 `JOIN`을 사용하여 전체 프로세스에서 쿼리가 단 한 번만 실행되도록 한다.
- **단건 조회 | `SELECT m FROM Member m WHERE m.id = 1`:**
  - **JPQL은 엔티티의 로딩 전략을 사전에 고려하지 않고, 일단 작성된 쿼리를 그대로 DB에 실행**한다.
  - DB에서 멤버 데이터를 가져와 객체로 만드는 과정에서, 뒤늦게 `Team`이 EAGER 설정인 것을 확인한다.
  - 연관된 `Team` 데이터를 채우기 위해 팀을 조회하는 추가 쿼리를 실행한다.
  - 결과적으로, 단건을 조회했음에도 총 2번(1+1)의 쿼리가 발생한다.
- **다건 조회 | `SELECT m FROM Member m`:**
  - JPQL을 이용한 단건 조회에서 느꼈던 "일단 쿼리를 실행한다"에 대한 반동이 훨씬 강해진다.
  - 결론부터 말하면, **단순히 멤버 테이블을 조회했을 뿐인데 내부적으로 쿼리가 N+1번 발생**하는 상황이다.
  - **프로세스:**
    1. 전체 멤버를 가져오는 최초 쿼리를 실행한다.
    2. DB에서 N건의 회원 레코드가 반환된다.
    3. JPA가 N개의 회원 객체를 생성하던 중, `Team`이 `EAGER`인 것을 뒤늦게 확인한다.
    4. N명의 회원 각각에 대해 연관된 Team 데이터를 채워 넣기 위해, 팀을 조회하는 쿼리를 개별적으로 실행한다.
    5. 결과적으로, 총 N+1번(1+N)의 쿼리가 발생한다.
