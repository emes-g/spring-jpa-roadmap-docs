## 스프링의 탄생 배경: EJB의 겨울

### EJB (Enterprise Java Beans) 시대
2000년대 초반, 자바 진영의 표준 기술이자 "종합 선물 세트"였다.

* **특징**
    * 트랜잭션, 분산 처리, 보안 등 기업 환경에 필요한 고급 기술을 모두 지원.
* **문제점 (지옥의 EJB)**
    * **비용:** 서버 한 대당 수천만 원에 달하는 고가의 장비와 소프트웨어가 필요함.
    * **복잡성:** 이론은 좋았으나, 실제 구현이 너무 어렵고 복잡함.
    * **침투적(Intrusive):** EJB가 제공하는 인터페이스를 상속받거나 구현해야 해서, 비즈니스 로직이 특정 기술(EJB)에 종속됨. -> **코드가 지저분해짐.**
    * **속도:** 매우 느리고 무거움.

### POJO (Plain Old Java Object)의 등장
EJB의 복잡성에 지친 개발자들이 **"옛날의 순수한 자바 객체로 돌아가자!"** 라고 외치며 나온 단어이다.

> **Q. POJO란?**
> * **정의:** 오래된 방식의 단순한 자바 객체.
> * **의미:** `extends EJBObject` 처럼 특정 프레임워크나 기술에 종속되지 않은, **순수한 자바 클래스**를 말한다.
> * **목적:** "기술은 숨기고, 핵심 비즈니스 로직은 깔끔한 순수 자바 객체(POJO)로 작성하자"는 철학이다.

## 두 영웅의 등장: Spring & Hibernate

EJB의 문제점(**비용, 복잡성, 종속성, 속도 문제**)을 해결하기 위해 오픈소스 진영에서 두 가지 핵심 기술이 등장했다.

### 스프링 (Spring) - 로드 존슨
* **역할:** EJB 컨테이너 대체.
* **특징:** EJB 없이도 고품질의 엔터프라이즈 애플리케이션 개발을 가능하게 함.
* **현재:** 사실상 표준 기술(De facto standard)로 자리 잡음.

### 하이버네이트 (Hibernate) - 개빈 킹
* **역할:** EJB 엔티티 빈(ORM 기술) 대체.
* **배경:** EJB 엔티티 빈이 너무 형편없어서, 개빈 킹이 "내가 만들어도 이것보단 낫겠다"며 만든 오픈소스.
* **결과:** EJB 엔티티 빈을 완전히 시장에서 사장시킴.

## JPA (Java Persistence API)의 탄생

### 표준 기술과 구현체
> **Q. 표준 기술과 구현체란?**
> * **표준 기술 (Interface):** 
>   * 자바 커뮤니티(JCP)에서 정한 **"설계도(명세서)"** 
>   * 껍데기(인터페이스)만 있고 실제 기능은 없음 (예: JPA)
> * **구현체 (Implementation):** 
>   * 설계도를 보고 실제 기능을 만든 **"제품"** (예: Hibernate, EclipseLink 등)

### JPA의 역사와 구조
1.  **Hibernate의 승리:** EJB 엔티티 빈이 망하고 Hibernate가 대세가 됨.
2.  **자바 진영의 흡수:** 자바 진영이 Hibernate 개발자(개빈 킹)를 데려와서 Hibernate를 거의 복사하다시피 하여 **표준 기술(JPA)** 을 만듦.
3.  **구조:**
    * **JPA:** 표준 인터페이스 (Standard Interface)
    * **Hibernate:** JPA의 가장 대표적인 구현체 (Implementation)

> **결론:** JPA라는 표준 인터페이스를 사용하면, 구현체를 Hibernate에서 다른 것으로 바꾸더라도 코드 변경을 최소화할 수 있다.

## 스프링의 역사와 탄생

### 시작: 로드 존슨과 "봄(Spring)"
* **기원:** 2002년, 로드 존슨(Rod Johnson)이 출간한 책 *Expert One-on-One J2EE Design and Development*에서 시작되었다.
* **증명:** 당시 주류였던 **EJB 없이도** 충분히 고품질의 확장 가능한 애플리케이션을 개발할 수 있음을 코드로 증명했다.
* **이름의 유래:** J2EE(EJB)라는 **"추운 겨울"** 을 넘어 새로운 시작이라는 뜻으로 **"봄(Spring)"** 이라고 지었다.

> **Q. J2EE가 EJB인가? 뭐가 다른지?**
> * **J2EE (Java 2 Enterprise Edition):** 자바를 이용해 기업용 애플리케이션을 만들 때 필요한 **모든 기술의 집합(플랫폼)** 이다. (현재의 Jakarta EE)
> * **EJB (Enterprise Java Beans):** J2EE 플랫폼 안에서 비즈니스 로직을 담당하는 **핵심 컴포넌트 기술**이다.
> * **관계:** 
>   * J2EE가 더 큰 개념이고, EJB는 그 안에 포함된 기술이다. 
>   * 하지만 당시에는 "J2EE를 쓴다 = EJB를 쓴다"와 거의 동의어였고, 스프링은 이러한 J2EE(특히 EJB)의 복잡함을 비판하며 등장했다.

## 스프링 부트 (Spring Boot)의 등장

### 배경: "설정 지옥(Configuration Hell)"
스프링은 기능이 너무 좋았지만, 초기 설정이 매우 힘들었다.
* **복잡한 설정:** 수많은 XML 설정 파일과 의존성 관리가 필요했다.
* **배포의 불편함:** 개발 후 WAS(Tomcat 등)를 별도로 설치하고, WAR 파일을 빌드해서 특정 폴더에 넣고 실행해야 했다.

### 해결책
이에 스프링 부트가 **"설정보다는 관례(Convention over Configuration)"** 를 내세우며 등장했다.
* **자동 설정:** 복잡한 설정을 스프링이 알아서 다 해준다.
* **내장 톰캣:** 톰캣을 프로젝트 안에 내장(Embedded)하여, 별도 설치 없이 `main` 메서드 실행만으로 서버를 띄울 수 있게 되었다.

## 스프링 5와 리액티브 프로그래밍 (2017~)

### 배경: 기존 서블릿 스택(Spring MVC)의 한계
초기 스프링은 자바 엔터프라이즈 표준인 **서블릿(Servlet)** 기반으로 설계되었다. 이는 안정적이지만, 트래픽이 폭증하는 현대의 환경에서는 구조적인 한계에 직면할 수 밖에 없었다.

* **Thread per Request 모델**
    * 요청(Request) 하나당 스레드 하나를 할당한다.
    * 요청이 처리되는 동안(DB 조회, 외부 API 호출 등) 해당 스레드는 **블로킹(Blocking)** 상태가 되어 아무 일도 하지 않고 대기한다.
* **스레드 지옥 (Thread Hell)**
    * 동시 접속자가 늘어나면 스레드 풀(Thread Pool)의 사이즈를 늘려야 한다.
    * 스레드가 많아지면 CPU가 스레드를 교체하는 **컨텍스트 스위칭(Context Switching)** 비용이 기하급수적으로 증가하여, 실제 작업보다 스레드 교체에 더 많은 자원을 쓰게 된다.
    * 결국 메모리 부족이나 CPU 과부하로 서버가 다운되는 현상이 발생하게 된다.

### 변화: 리액티브 스택 (Spring WebFlux)의 도입
2017년 스프링 5.0은 이러한 Blocking I/O의 한계를 극복하기 위해, **Node.js**와 유사한 **비동기 넌블로킹(Asynchronous Non-blocking)** 모델을 자바 진영에 공식적으로 도입했다.

* **Spring WebFlux**
    * 기존 Spring MVC를 대체/보완하는 새로운 웹 프레임워크이다.
    * **이벤트 루프(Event Loop)** 방식을 사용하여, 소수의 스레드(일반적으로 CPU 코어 수 * 2)만으로 대량의 요청을 처리한다.
* **Netty 서버 사용**
    * 기존의 톰캣(Tomcat) 대신, 비동기 처리에 최적화된 **Netty**를 기본 서버로 사용한다.
* **프로젝트 리액터 (Project Reactor)**
    * 리액티브 스트림(Reactive Streams) 표준을 구현한 라이브러리로, 데이터를 **스트림(Stream)** 형태로 흘려보내며 처리한다.

### 리액티브 프로그래밍의 핵심 가치
* **높은 처리량 (High Throughput):** 적은 하드웨어 리소스로 더 많은 동시 요청을 처리할 수 있다.
* **확장성 (Scalability):** 스레드를 무한정 늘리지 않아도 되므로, 마이크로서비스(MSA) 환경이나 클라우드 환경에서 시스템 확장이 유리하다.
* **백프레셔 (Backpressure):** 데이터를 소비하는 쪽(Subscriber)이 처리할 수 있는 양만큼만 데이터를 요청하여, 시스템 과부하를 방지하는 흐름 제어 기능을 제공한다.

## 핵심 개념: 동기/비동기 vs 블로킹/넌블로킹

이 두 개념은 **Caller(호출자)의 의도**와 **Callee(피호출자)의 태도**로 구분하면 가장 명확하다.

### 구분 기준
#### 1.  **동기 vs 비동기 (주체: Caller)**
> **Caller가 지금 무엇을 하고 싶은가?** 
* **동기(Sync):** Caller는 응답을 기다리고 싶어 한다. (결과에 관심이 있음)
* **비동기(Async):** Caller는 응답을 기다리지 않고, 바로 다음 일을 하러 가고 싶어 한다. (결과 처리를 위임함)

#### 2.  **블로킹 vs 넌블로킹 (주체: Callee)**
> **Callee가 Caller의 제어권을 갖고 있을 것인가?**
* **블로킹(Blocking):** Callee가 Caller의 제어권을 가지고 있다.
  * **Caller의 의도(동기/비동기)와는 관계 없이 Caller는 Callee만을 바라보게 된다.**
* **넌블로킹(Non-blocking):** Callee가 Caller의 제어권을 즉시 반환해 준다.

## I/O 모델 4가지 조합 분석

### 동기 + 블로킹 (Sync + Blocking)
> **Caller는 응답을 기다리고, Callee는 Caller의 제어권을 가지고 있는 상태.**

* **상황:** 전통적인 자바의 입출력(InputStream/OutputStream), JDBC.
* **분석:** Caller는 애초에 응답을 기다리려고 했는데(Sync), Callee에게 제어권도 뺏긴 상태(Blocking)이다.
* **결과:** 스레드 대기 발생
  * 제어권도 없고 응답도 기다려야 하므로, 응답이 올 때까지 **꼼짝없이 대기**한다.

### 비동기 + 넌블로킹 (Async + Non-blocking)
> **Caller는 다음 일을 하려고 하고, Callee는 Caller의 제어권을 곧바로 반환해준 상태.**

* **상황:** **Spring WebFlux**, Node.js, Netty.
* **분석:** Caller는 애초에 다음 일을 하려고 했는데(Async), 마침 Callee가 제어권도 바로 반환해준 상태(Non-blocking)이다.
* **결과:** 리소스 효율 극대화
  * Caller는 **마음 편하게(Callee를 전혀 신경 쓰지 않고)** 다음 일을 처리하러 간다.

### 동기 + 넌블로킹 (Sync + Non-blocking)
> **Caller는 응답을 기다리고, Callee는 Caller의 제어권을 곧바로 반환해준 상태.**

* **상황:** **폴링(Polling)**. (예: Java NIO의 일부 동작)
* **분석:** Caller는 응답을 기다리려고 했는데(Sync), Callee가 제어권을 반환해줘서(Non-blocking) 일단 다음 일을 하러 갈 수 있는 상태가 되었다.
* **결과:** 지속적인 확인으로 인한 CPU 낭비 가능성 
  * 다른 일을 할 수는 있지만, 애초에 응답을 기다리려던 목적 때문에 **마음이 불편해서 계속 Callee를 신경 쓰며(확인하며)** 작업을 진행한다.

### 비동기 + 블로킹 (Async + Blocking)
> **Caller는 다음 일을 하려고 했지만, Callee가 Caller의 제어권을 가지고 있는 상태.**

* **상황:** **안티 패턴 (Anti-pattern)**. (예: WebFlux 환경에서 JDBC 사용)
* **분석:** Caller는 다음 일을 하러 가고 싶었으나(Async), Callee가 제어권을 놔주지 않는 상태(Blocking)이다.
* **결과:** 시스템 성능 저하 
  * 의도는 비동기였으나 제어권이 묶여버렸기 때문에, 마치 **동기+블로킹처럼 대기**해야만 한다.

## 스프링 생태계 (Spring Ecosystem)

스프링은 특정한 하나의 기술이 아니라, 여러 기술들의 모음이다.

### 주요 기술
* **Spring Framework:** 가장 핵심이 되는 기술. (DI 컨테이너, AOP, MVC, 트랜잭션 등)
* **Spring Boot:** 스프링 프레임워크를 포함한 다양한 스프링 기술들을 편리하게 사용할 수 있도록 도와주는 기술.
* **Spring Data:** 데이터 접근 기술(JPA, Redis, Mongo 등)을 편리하게 사용할 수 있도록 돕는 모듈. (CRUD 단순화)
* **Spring Session:** 세션 기능을 편리하게 사용할 수 있도록 지원.
* **Spring Security:** 강력한 보안(인증/인가) 프레임워크.
* **Spring Rest Docs:** 테스트 코드를 기반으로 API 문서를 자동으로 만들어주는 도구.
* **Spring Batch:** 대용량 데이터 처리에 최적화된 배치 처리 프레임워크.
* **Spring Cloud:** 분산 시스템(마이크로서비스) 개발에 필요한 도구 모음.

> **참고:** `spring.io` 사이트에서 수많은 프로젝트 확인 가능.

## 스프링 프레임워크와 스프링 부트

### 스프링 프레임워크 (The Foundation)
**스프링 생태계의 모든 기술들은 이 '스프링 프레임워크'를 기반으로 동작한다.**

* **정의:** 스프링 생태계의 모든 기술들(Boot, Data, Security 등)의 기반이 되는 **핵심 기술의 총칭**이다.
* **핵심 기술:** DI 컨테이너, AOP, 이벤트, 기타
* **웹 기술:** 스프링 MVC, 스프링 WebFlux
* **데이터 접근:** 트랜잭션, JDBC, ORM 지원, XML 지원
* **기타:** 캐시, 이메일, 스케줄링 등

### 스프링 부트 (The Wrapper)
**스프링 프레임워크(기반 기술)를 편리하게 사용할 수 있도록 도와주는 '도구'이다.**

* **관계:** 
  * 스프링 부트는 별도의 기술이 아니다. 
  * 내부적으로 **스프링 프레임워크를 품고 있으며**, 이를 쉽게 사용할 수 있도록 감싸주는(Wrap) 역할을 한다.
* **주요 기능:**
    1.  **단독 실행:** Tomcat 같은 웹 서버를 내장(Embedded)하여 별도의 웹 서버 설치 없이 `java -jar`로 실행 가능.
    2.  **쉬운 의존성 관리:** `starter` 종속성을 제공하여, 라이브러리 간의 버전 조합(호환성)을 신경 쓰지 않아도 됨.
    3.  **관례에 의한 설정 (Convention over Configuration):** 복잡한 설정을 자동으로 처리.

#### Q. '관례에 의한 설정'이란 무엇인가요?
> **"네가 특별히 말하지 않으면, 우리(스프링)가 정한 표준(관례)대로 다 세팅해줄게."**

* **의미:** 개발자가 일일이 설정 파일(XML 등)을 만지지 않아도, 스프링 부트가 자주 사용되는 패턴을 미리 파악하고 **자동으로 설정(Auto Configuration)** 해 주는 것이다.
* **예시:** `spring-boot-starter-web` 라이브러리만 추가하면, 스프링 부트는 *"아, 너 웹 개발 하려는구나? 그럼 내가 알아서 톰캣 띄우고, 포트는 8080으로 잡고, JSON 변환기(Jackson)도 끼워 넣어줄게"* 라고 판단하여 자동으로 구성한다.

---

## '스프링'이라는 단어의 의미

문맥에 따라 다르게 해석된다.

1.  **스프링 DI 컨테이너:** 빈을 관리하는 핵심 기술 (가장 좁은 의미).
2.  **스프링 프레임워크:** DI 컨테이너를 포함한 핵심 라이브러리 집합.
3.  **스프링 생태계:** 스프링 부트, 스프링 데이터 등을 모두 포함한 전체 (가장 넓은 의미).

---

## 스프링의 핵심 개념과 철학

### 왜 만들었는가?
* **기반:** 자바 언어 기반의 프레임워크.
* **자바의 특징:** **객체 지향 언어 (Object Oriented Programming).**
* **스프링의 본질:** 자바 언어가 가진 **가장 강력한 특징인 '객체 지향'을 살려내는 것.**

> **결론:**
> 스프링은 단순히 기능을 제공하는 도구가 아니라, **"어떻게 하면 좋은 객체 지향 애플리케이션을 개발할 수 있을까?"** 를 고민하고 도와주는 프레임워크이다.

---

## 객체 지향 프로그래밍 (Object-Oriented Programming)

### 객체 지향의 특징
* **협력(Cooperation):** 객체들은 서로 메시지를 주고받으며 협력한다.
* **유연성과 변경 용이성:**
    * 컴포넌트를 쉽고 유연하게 변경하면서 개발할 수 있다.
    * **비유:** 레고 블럭 조립하듯이, 키보드/마우스를 갈아 끼우듯이, 컴퓨터 부품을 업그레이드하듯이 소프트웨어를 변경할 수 있다.
    * **핵심:** 이것을 가능하게 하는 것이 바로 **다형성(Polymorphism)** 이다.

---

## 역할과 구현의 분리 (Role and Implementation)

실제 세상을 **역할(Role)** 과 **구현(Implementation)** 으로 구분하면 세상이 단순하고 유연해진다. (변경이 용이해진다)

### 실세계의 비유: 운전자와 자동차
* **상황:** 자동차가 K3에서 아반떼로 바뀌어도, 운전자에게는 영향을 주지 않는다.
* **이유:** 
  * 운전자는 '자동차의 역할(운전 방법)'만 알고 있으면 되기 때문이다. 
  * 즉, 내부 엔진이 어떻게 바뀌든(구현의 변경) 상관없다.

### 핵심 개념
* **역할:** 인터페이스 (Interface)
* **구현:** 인터페이스를 구현한 객체 (Implementation Class)

### 장점 (클라이언트 관점)
1.  **단순함:** 클라이언트는 대상의 **역할(인터페이스)** 만 알면 된다.
2.  **내부 은닉:** 클라이언트는 구현 대상의 **내부 구조를 몰라도** 된다.
3.  **유연함:**
    * 구현 대상의 **내부 구조가 변경**되어도 클라이언트는 영향을 받지 않는다.
    * 심지어 **구현 대상 자체를 변경**해도 클라이언트는 영향을 받지 않는다.

> **설계 원칙:**
> 객체를 설계할 때 **역할(인터페이스)을 먼저 부여**하고, 그 역할을 수행하는 **구현 객체**를 만들어야 합니다.

---

## 다형성의 실체와 Java

### 협력 관계 (Client & Server)
* **클라이언트:** 요청하는 객체.
* **서버:** 요청을 받아 응답하는 객체.
* 수많은 객체 클라이언트와 객체 서버가 서로 **협력 관계(의존 관계)** 를 맺는다.
> 객체들이 서로 메세지를 주고받는 것을 **협력한다**고 표현한다.

### 자바 언어의 다형성
* **오버라이딩(Overriding):**
    * 인터페이스를 구현한 객체를 실행 시점에 유연하게 변경할 수 있다.
    * 다형성으로 인해 **오버라이딩된 메서드가 실행**된다.
* **의존(Dependency):**
    * "의존한다"는 것은 "내가 쟤를 알고 있다"는 뜻이다.
    * `MemberService`(클라이언트)는 `MemberRepository`(인터페이스)에 의존한다.
    * 다형성에 의해 부모 타입(인터페이스)으로 구현체들을 다 받아들일 수 있게 된다.

### 다형성의 본질
> **"클라이언트를 변경하지 않고, 서버의 구현 기능을 유연하게 변경할 수 있다."**

* 인터페이스를 구현한 객체 인스턴스를 **실행 시점(Runtime)** 에 유연하게 변경할 수 있는 것이 핵심이다.
* 이를 이해하려면 객체 하나만 보는 것이 아니라, **협력**이라는 객체 사이의 관계에서 바라봐야 한다.

---

## 다형성의 힘과 한계

### 다형성의 힘
* 실세계의 '역할과 구현'이라는 편리한 컨셉을 객체 세상으로 가져올 수 있다.
* 시스템이 유연하고 변경이 용이해지며, **확장 가능한 설계**가 된다.

### 인터페이스 설계의 중요성 (다형성의 한계)
* **안정성:** 역할(인터페이스) 자체가 변하면, 클라이언트와 서버 모두에게 큰 변경이 발생한다. (대공사 발생)
* 따라서, API(인터페이스)를 **최대한 변경이 없도록 안정적으로 잘 설계**하는 것이 가장 중요하다.

---

## 스프링과 객체 지향

> **"스프링은 다형성을 극대화해서 이용할 수 있게 도와주는 프레임워크"**

* **스프링의 역할:**
    * 스프링에서 이야기하는 **IoC(제어의 역전)**, **DI(의존관계 주입)** 는 결국 **다형성**을 활용해 역할과 구현을 편리하게 다룰 수 있도록 지원하는 기술이다.
    * 스프링을 사용하면 마치 레고 블럭 조립하듯이, 공연 무대의 배우를 교체하듯이 **구현을 편리하게 변경**할 수 있다.

* **결론:**
    * 스프링과 객체 지향 설계를 제대로 이해하려면 **다형성**만으로는 부족하다.
    * **SOLID (좋은 객체 지향 설계의 5가지 원칙)** 를 함께 알아야 비로소 스프링을 설명할 수 있게 된다.

---

## 좋은 객체 지향 설계의 5가지 원칙 (SOLID)

### 1. SRP: 단일 책임 원칙 (Single Responsibility Principle)
> **"한 클래스는 하나의 책임만 가져야 한다."**

* **모호함:** '하나의 책임'이라는 말은 문맥과 상황에 따라 클 수도 있고 작을 수도 있어 모호하다.
* **중요한 기준:** **변경(Change)** 이다.
    * 변경이 있을 때 파급 효과가 적으면 SRP를 잘 따른 것이다.
    * 예: UI를 변경하는데 SQL 코드나 비즈니스 로직까지 고쳐야 한다면 SRP 위반이다.
    * **핵심:** 변경이 발생했을 때, **딱 하나의 클래스나 지점만 고치면** 된다.

### 2. OCP: 개방-폐쇄 원칙 (Open/Closed Principle) ★
> **"소프트웨어 요소는 확장에는 열려 있으나, 변경에는 닫혀 있어야 한다."**

* **의미:** 기존(클라이언트) 코드를 변경하지 않고(Closed), 새로운 기능을 추가(Open)할 수 있어야 한다.
* **방법:** 
  * **다형성**을 활용한다. 
  * 즉, 새로운 구현체(인터페이스를 구현한 새로운 클래스)를 만들어서 새로운 기능을 구현한다.

#### 다형성의 한계: 다형성만으로는 OCP를 준수할 수 없다.
```java
// 구현체를 Memory에서 Jdbc로 바꾼다고 하자.
// MemberRepository m = new MemoryMemberRepository();
MemberRepository m = new JdbcMemberRepository();
```
* **분석:**
  * 분명 다형성을 사용했지만, 구현 객체를 변경하기 위해 **클라이언트 코드를 변경**하고 있다.
  * 이는 '기존 코드를 변경하지 않고(Closed)'를 만족하지 못하므로 OCP 위반이다.
* **결론:** 객체를 생성하고 연관 관계를 맺어주는 별도의 **조립, 설정자(Spring Container)** 가 필요하다.

### 3. LSP: 리스코프 치환 원칙 (Liskov Substitution Principle)
> **"프로그램의 객체는 프로그램의 정확성을 깨뜨리지 않으면서 하위 타입의 인스턴스로 바꿀 수 있어야 한다."**

* **의미:**
  * **프로그램의 정확성을 깨뜨리지 않으면서:** 인터페이스 규약(메서드의 설계 의도)을 만족하면서
  * **하위 타입의 인스턴스로 바꿀 수 있어야 한다:** 부모 인터페이스를 사용하는 자리에 자식 구현체를 넣어도 시스템이 문제없이 돌아가야 한다.
  * 이는 컴파일 성공 여부 차원의 이야기가 아니다.
* **핵심:** 구현체를 믿고 사용하려면 LSP가 필요하다.
* **예시 (자동차 엑셀):**
    * 자동차 인터페이스의 '엑셀' 기능은 "앞으로 간다"는 규약이 있다고 하자.
    * 만약 하위 클래스가 '엑셀'을 밟았는데 "뒤로 가게" 구현했다면?
    * 컴파일은 되지만 규약을 위반했으므로 **LSP 위반**이다. (느리더라도 앞으로는 가야 함)

### 4. ISP: 인터페이스 분리 원칙 (Interface Segregation Principle)
> **"특정 클라이언트를 위한 인터페이스 여러 개가 범용 인터페이스 하나보다 낫다."**

* **의미:**
  * 범용 인터페이스 대신, 기능에 맞게 인터페이스를 잘게 쪼개야 한다.
* **장점:** 
  * 인터페이스 변동의 영향을 최소화 할 수 있다.
  * 인터페이스가 명확해지고, 대체 가능성이 높아진다.
* **예시:**
  * 자동차 인터페이스 -> **운전 인터페이스**, **정비 인터페이스**로 분리하고,
  * 사용자 클라이언트 -> **운전자 클라이언트**, **정비사 클라이언트**로 분리했다고 하자.
  * 그러면 정비 인터페이스가 변해도 운전자 클라이언트에게는 영향을 주지 않는다.

### 5. DIP: 의존관계 역전 원칙 (Dependency Inversion Principle) ★ 
> **"추상화에 의존해야지, 구체화에 의존하면 안 된다."**

* **의미:** 구현 클래스(구현) 대신, **인터페이스(역할)** 에 의존하라는 뜻이다.
* **이유:** 클라이언트(요청을 하는 객체)가 인터페이스에만 의존해야 유연하게 구현체를 변경할 수 있기 때문이다.

#### 클라이언트는 구현체를 몰라야 한다.
```java
// MemberService 클라이언트 코드
MemberRepository m = new MemoryMemberRepository();
```
* **분석:**
    * `MemberService`는 `MemberRepository`(인터페이스)에 의존하고 있다. (Good)
    * **하지만** 동시에 `MemoryMemberRepository`(구현 클래스)도 의존하고 있다. (Bad)
* **결론:** 
  * 클라이언트가 구현 클래스를 직접 선택하고 있으므로(알고 있으므로, import 했으므로) **DIP 위반**이다. 
  * 위 사례에서는 구현체를 바꾸려면 클라이언트 코드를 고쳐야 한다.

---

## 정리: 객체 지향의 핵심과 다형성

### 다형성 (Polymorphism)이란?
* **기본 정의:** 부모 타입의 변수에 자식 타입의 객체를 넣을 수 있는 능력
* **확장된 의미 (역할과 구현): 하나의 역할(인터페이스)에 대해 다양한 구현(객체)을 갈아 끼울 수 있는 능력** 
* 이를 통해 클라이언트는 대상의 역할만 알면 되고, 내부 구현이 바뀌어도 영향을 받지 않게 된다.

### 다형성의 한계
* 객체 지향의 핵심은 다형성이 맞지만, **다형성만으로는 OCP, DIP를 지킬 수 없다.**
* 다형성만으로는 구현 객체를 변경할 때 **클라이언트 코드도 함께 변경**되어야 한다. (OCP, DIP 위반)
* **결론:** 
  * OCP, DIP를 준수하기 위해 다형성 외에 무언가가 더 필요하다. 
  * 이것이 바로 스프링(DI 컨테이너)이 탄생한 이유이다.

---

## 개발 단계 용어 정리: 컴파일 vs 빌드 vs 런타임

### 1. 컴파일 (Compile)
> **소스 코드(`.java`)를 기계어(바이트코드, `.class`)로 변환하는 과정** 
* **정의:** 사람이 작성한 소스 코드(`Java`)를 컴퓨터(JVM)가 이해하고 실행할 수 있는 기계어(바이트코드, `.class`)로 변환하는 과정이다.
* **시점:** 프로그램 실행 전, 소스 코드를 작성한 후 빌드 단계의 초입에서 발생한다.
* **에러(Compile Error):** 
  * 문법 오류(Syntax Error), 타입 불일치 등 프로그래밍 언어의 규칙을 위반했을 때 발생한다. 
  * 이 에러가 해결되지 않으면 프로그램 실행 파일 자체가 생성되지 않는다.

### 2. 빌드 (Build)
> **실제 실행 가능한 파일(`.jar`, `.war`)을 만드는 과정**
* **정의:** 소스 코드를 컴파일하고, 단위 테스트를 수행하며, 필요한 라이브러리 및 자원(Resource)을 통합하여 **실제 실행 가능한 산출물(`.jar`, `.war`)로 만드는 일련의 과정**을 의미한다.
* **포함 관계:** `컴파일`은 `빌드` 과정의 일부 단계이다. (Build ⊇ Compile)
* **결과물:** 배포 및 실행이 가능한 아티팩트(Artifact).

### 3. 런타임 (Runtime)
> **컴파일 및 빌드를 마친 프로그램이 메모리에 적재되어 실행 중인 상태**
* **정의:** 컴파일과 빌드 과정을 마친 프로그램이 메모리에 적재되어 **실제로 실행되고 있는 시간(동작 중인 상태)** 을 의미한다.
* **에러(Runtime Error):** 
  * 프로그램 실행 도중에 발생하는 예외 상황이다. (0으로 나누기, NullPointer, 메모리 부족 등) 
  * 컴파일 단계에서 감지하지 못한 논리적 결함이나 환경적 요인으로 인해 발생하며, 프로그램의 비정상 종료나 오동작을 유발한다.

## 스프링과 객체 지향 설계

### 스프링의 탄생 배경과 역할
* **DI 컨테이너의 역할:** 
  * 다형성뿐만 아니라 OCP, DIP를 가능하게 지원한다. 
  * 이를 통해 **클라이언트 코드의 변경 없이 기능을 확장**할 수 있다.
* **탄생 배경:**
    * 순수 자바 코드로만 OCP, DIP 원칙을 완벽하게 지키려다 보니, 배보다 배꼽이 더 커지는 상황(비즈니스 로직보다 객체 생성 및 연결 코드가 더 복잡해짐)이 발생했다.
    * 이러한 구조적인 복잡함을 해결하고 원칙을 편리하게 적용하기 위해 프레임워크(스프링)가 만들어졌다.

### 이상적으로는 모든 곳에서 '역할'과 '구현'을 분리하는 것이 좋다.
> **장점: 결정의 유보(Deferring Decisions)**
* 인터페이스를 사용하면 하부 구현체에 대한 구체적인 결정을 나중으로 미룰 수 있다.
* **예시 (할인 정책):**
    * 아직 할인 정책이 기획되지 않았더라도 개발을 멈출 필요가 없다.
    * `DiscountPolicy` 인터페이스와 `FixDiscountPolicy`(또는 0원 할인) 같은 임시 구현체를 만들어두고 전체 로직을 개발하면 되기 때문이다.
    * 나중에 기획이 확정되면 구현체만 교체(Switching)하면 된다.

### 하지만 추상화 비용이 발생한다.
> 인터페이스 도입은 공짜가 아니다. **추상화 비용**이 발생한다.

* **의미:** 런타임 성능 저하가 아니라, **개발자의 인지 비용(Cognitive Load)** 을 의미한다.
* **단점:** 
  * 코드가 추상화되면, 실제 코드가 어떻게 동작하는지 파악하기 위해 인터페이스를 거쳐 구현 클래스를 **한 번 더 열어봐야(Navigate)** 한다.
  * 즉, 코드를 직관적으로 파악하기 어려워진다.
* **결론:** 무조건 인터페이스를 도입하는 것이 정답이 아니며, **장점이 단점(비용)을 넘어설 때** 선택해야 한다.

### 따라서 실무에서는 '기능의 확장 가능성'을 생각하여 결정한다.
> **"기능을 확장할 가능성이 있는가?"**

1.  **확장 가능성이 없다면:**
    * 바로 **구체 클래스(Concrete Class)** 를 직접 사용한다.
    * 향후 꼭 필요할 때 리팩터링을 통해 인터페이스를 도입해도 늦지 않는다. (YAGNI 원칙)
2.  **확장 가능성이 있다면:**
    * 처음부터 **인터페이스**를 도입하여 유연하게 설계한다.

### 그렇기에 개발자와 아키텍트의 경계는 모호하다.
* 추상화 비용과 유연함 사이의 트레이드오프를 결정하는 것은 코드 레벨에서 빈번하게 일어난다.
* 따라서 단순히 '구현하는 사람(Developer)'과 '설계하는 사람(Architect)'을 명확히 분리하는 것은 어렵다. 
* 좋은 개발자는 이러한 아키텍처적 판단을 코드 작성 시점에 내릴 수 있어야 한다.
