## HTTP API
### API 설계란?
> **클라이언트와 서버가 통신하기 위한 전체적인 규격을 모두 정의하는 포괄적인 개념**이다.

- URI 경로, HTTP 메서드, 주고받을 JSON 데이터 포맷, 응답 상태 코드 등 **웹 통신에 필요한 모든 데이터의 형식(포맷)을 정의하는 일련의 과정**을 의미한다.
- 이때 API 설계의 코어 작업이 **대상이 되는 리소스를 어떻게 식별할 것인가**, 즉 **URI 설계**이다.
- 정리하면 **API 설계와 URI 설계가 동일하진 않지만, API 설계의 코어 작업이기 때문에 URI 설계가 중요하다** 정도로 이해하면 될 것 같다.   

### URI 설계
- '회원 관리 API를 구축하라'는 요구사항이 주어졌다고 하자.
- 앞서 확인했듯, **API 설계의 첫 단계는 대상 리소스에 대한 URI를 설계하는 것**으로, 이때 URI는 **일관되게 '리소스'를 식별할 수 있는 방법**이라고 정의했다.
- 즉, **URI의 목적은 리소스를 식별하는 것에 있으므로, URI를 설계할 때는 '조회/등록/수정/삭제'와 같은 동사 형태의 행위가 포함되어서는 안 된다.**

### 리소스와 행위의 분리
> **URI로 리소스를 식별하고, HTTP Method로 대상 리소스에 대한 행위를 파악**한다. 

- 행위를 완전히 배제한다면, 오직 명사 형태의 리소스만 사용해서 `/members` 혹은 `/members/{id}`와 같은 형태로 URI를 설계해야 한다.
- 하지만 이처럼 **리소스만으로 URI를 구성할 경우** 클라이언트의 행위, 즉 **클라이언트가 해당 대상에 대해 구체적으로 어떤 동작을 수행하려는지 파악(구분)할 수 없게 된다.**
- 이를 해결하기 위해, HTTP API 설계에서는 **URI로 리소스만을 식별**하고, **해당 리소스에 대한 구체적인 행위는 HTTP 메서드에 위임**하는 방식으로 **역할과 책임을 분리**하였다.

## HTTP Method
### 개요
- **GET:** 대상 리소스 조회
- **POST:** 요청 데이터 처리 (주로 신규 리소스 등록)
- **PUT:** 대상 리소스 대체(덮어쓰기)
- **PATCH:** 대상 리소스의 데이터를 부분 수정
- **DELETE:** 대상 리소스 삭제
- **HEAD:** GET과 동일하나, **응답 메시지에서 바디 없이 status-line과 header만 반환**된다.

### GET: 리소스 조회
> **대상 리소스를 서버에 요청하여 가져올 때 사용**한다.

- 조회를 목적으로 하므로 요청 메시지 바디에 데이터를 넣지 않는 것이 원칙이다.
- **서버에 전달해야 할 부가적인 데이터(검색어, 필터 조건 등)는 URI의 쿼리를 통해 전달**한다.

### POST: 요청 데이터 처리
> **클라이언트가 요청 메시지 바디를 통해 서버로 데이터를 전달하고, 서버가 해당 데이터를 처리하도록 요구할 때 사용**한다.

#### 신규 리소스 생성
- **주로 새로운 데이터를 등록할 때 사용**한다.
- 등록 이후, 응답 시 `201 Created` 상태 코드와 함께 생성된 리소스의 위치(URI)를 Location 헤더에 담아 반환한다.

#### 프로세스 상태 처리
- 단순히 DB에 값을 등록하고 변경하는 것을 넘어, **서버 내부의 비즈니스 프로세스 상태를 변경할 때 사용**한다.
  - 예) 결제 완료 상태에서 배달 시작 상태로 변경
- **프로세스 처리에서도 명사 형태의 리소스만으로 URI 설계가 불가능한 경우, 예외적으로 동사를 포함**하는데 이를 **컨트롤 URI**라 한다.
  - 예) `/orders/{orderId}/start-delivery`

#### 조회 (예외적)
- **복잡한 검색 조건을 쿼리만으로 전달하기 어려워 메시지 바디에 데이터를 담아야 할 때**, 바디를 지원하지 않는 GET 대신 POST를 사용할 수 있다.
- 단, **GET 요청의 결과는 브라우저나 중간 서버에서 캐싱하여 사용하기 용이하지만, POST는 캐싱 매커니즘을 적용하기 어렵다.**
- 따라서 **조회 작업은 최대한 GET을 사용**하고, **POST에서는 리소스의 변경이나 프로세스 처리 작업을 수행**하도록 설계하는 것이 권장된다.

#### 결론
- `POST`는 사실 모든 일을 수행할 수 있으므로, 다른 메서드로 처리하기 애매하다거나, 잘 모르겠으면 `POST`를 사용해도 된다.
- 다만 **확실하게 다른 메서드로 처리할 수 있는데, 무분별하게 사용하는 것만 지양**하도록 하자.

### PUT: 리소스 대체(덮어쓰기)
> **요청한 URI에 대상 리소스가 존재하면 덮어쓰고, 존재하지 않으면 새로 생성**한다.

#### POST와의 차이점
- POST는 **클라이언트가 리소스 집합의 위치(`/members`)까지만 지정**하여 서버가 식별자를 생성하게 한다.
- 하지만, PUT은 **클라이언트가 변경할 리소스의 정확한 위치(`/members/100`)까지 지정**해야 한다.

#### 주의사항 (PATCH 등장 배경)
- **리소스를 부분적으로 수정하는 것이 아니라 완전히 대체**하는 것이므로, 기존 데이터 중 **일부 필드만 전송할 경우 나머지 필드 데이터는 모두 삭제**된다.

### PATCH: 리소스 부분 변경
> **대상 리소스의 특정 필드 데이터만 부분적으로 수정할 때 사용**한다.

- 일부 구형 웹 서버 환경에서는 PATCH 메서드를 지원하지 않는 경우가 있는데, 이럴 때는 POST 메서드를 사용하도록 한다.

### DELETE: 리소스 제거
> **클라이언트가 지정한 대상 리소스를 서버에서 완전히 삭제할 때 사용**한다.

## HTTP 메서드의 속성
### 안전 (Safe)
> **클라이언트가 해당 메서드를 호출해도, 대상 리소스 자체를 변경하지 않는 속성**이다.

- **리소스 조회를 하는 메서드(GET, HEAD)의 경우에만 해당하는 속성**이다.
- 해당 속성은 오직 호출 대상인 리소스의 변경 여부만을 기준으로 판단한다.
  - 호출로 인한 부수 효과(서버 로그 누적으로 인한 스토리지 장애 발생)는 고려하지 않는다. 

### 멱등 (Idempotent)
> **몇 번을 요청하든 서버에 반영되는 결과가 동일한 속성**이다.

- POST를 제외한 주요 메서드들은 멱등성을 보장한다.
- **POST 메서드는 매번 새로운 상태를 유발할 수 있으므로 멱등하지 않다.**
  - 결제가 여러 번 발생하는 경우
  - 게시글이 여러 개 생성되는 경우
- 멱등성은 네트워크 타임아웃이나 통신 장애 발생 시, **클라이언트가 동일한 요청을 자동으로 재전송해도 되는지 판단하는 근거**가 된다.
- 멱등성은 단일 클라이언트의 요청 맥락만 고려하므로, **외부 요인(다른 클라이언트의 개입)으로 인한 리소스 변경은 고려하지 않는다.**

### 캐시 가능 (Cacheable)
> **서버의 응답 결과를 클라이언트 로컬이나 브라우저 메모리에 저장(캐싱)하여 네트워크 요청 없이 재사용할 수 있는 속성**이다.

- 공식 스펙 상으로는 모든 주요 메서드가 캐싱 가능하지만, **실제로는 조회 메서드(GET, HEAD) 정도만 캐시 목적으로 사용**된다.
  - 조회 이외의 메서드들은 메시지 바디를 가지고 있기 때문에 캐시 키 설계가 복잡해지기 때문이다.

#### 캐시 키
> **저장소에서 특정 응답 데이터를 다시 가져오기 위해 사용하는 고유한 식별자**를 의미한다.

- 조회 메서드는 URL 자체를 식별자(키)로 쓰면 되므로 간편하다.
- 반면, **다른 메서드는 요청 메시지 바디의 데이터까지 포함해서 키로 만들어야 하는데, 이는 구현이 까다롭기 때문에 캐시해서 사용하지 않는다.**
